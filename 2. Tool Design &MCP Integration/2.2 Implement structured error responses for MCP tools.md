# Domain 2: Tool Design & MCP Integration

## Task Statement 2.2: Implement Structured Error Responses for MCP Tools

---

## 1. Introduction

Tools do not always succeed. A database may be down. A user may send bad input. A business rule may block an action. When a tool fails, **how it reports the failure** is just as important as the failure itself.

If every failure just says `"Operation failed"`, Claude (the agent) has no way to know:
- Should I try again?
- Should I ask the user for different input?
- Should I stop and explain the problem?

This tutorial covers how to design **structured error responses** so that Claude can make smart recovery decisions instead of guessing.

You will learn:

1. The MCP `isError` flag pattern
2. The four main error types: transient, validation, business, permission
3. Why generic error messages hurt agent performance
4. Retryable vs non-retryable errors
5. How to write structured error metadata
6. Local error recovery in subagents vs propagating to a coordinator
7. The difference between a real failure and a valid empty result

---

## 2. The MCP `isError` Flag Pattern

In the Model Context Protocol (MCP), a tool result can be marked as an error using a boolean flag called `isError`. This tells Claude, in a simple and consistent way: "this tool call did not succeed."

### 2.1 Basic Shape

```json
{
  "content": [
    { "type": "text", "text": "Description of what happened" }
  ],
  "isError": true
}
```

- `isError: true` → the tool call failed
- `isError: false` (or the field left out) → the tool call succeeded

### 2.2 Why a Flag Instead of Just Throwing an Exception?

MCP tools return results as normal messages, not raw exceptions. The `isError` flag lets the failure travel through the same channel as a success message, so Claude can read it, understand it, and decide what to do next — instead of the whole system crashing.

### 2.3 Simple Flow Diagram

```
Tool is called
      │
      ▼
Tool tries to do the work
      │
      ├── Success ──► isError: false  ──► Claude uses the result
      │
      └── Failure ──► isError: true   ──► Claude reads error info
                                              and decides what to do
```

**Important:** `isError: true` alone is not enough. It only tells Claude *that* something failed — not *why*, and not *what to do about it*. That is where structured error metadata comes in (covered in Section 5).

## 3. The Four Error Categories

Not all errors are the same, and Claude should not treat them the same way. There are four common categories.

### 3.1 Transient Errors

**What they are:** Temporary problems that may go away if you try again shortly.

**Examples:**
- Timeout while calling a downstream service
- "Service temporarily unavailable" (e.g. HTTP 503)
- Network hiccup

**Correct agent behavior:** Usually safe to retry, often after a short wait.

```json
{
  "isError": true,
  "errorCategory": "transient",
  "isRetryable": true,
  "message": "The weather service timed out. This is usually temporary."
}
```

### 3.2 Validation Errors

**What they are:** The input sent to the tool was invalid or incorrectly formatted.

**Examples:**
- Missing required field
- Wrong data type (e.g. text instead of a number)
- Date in the wrong format

**Correct agent behavior:** Retrying the exact same input will fail again. Claude should fix the input first (or ask the user for correct input).

```json
{
  "isError": true,
  "errorCategory": "validation",
  "isRetryable": false,
  "message": "The 'date' field must be in YYYY-MM-DD format. Received '12/05/2025'."
}
```

### 3.3 Business Errors (Policy Violations)

**What they are:** The request is technically valid, but it breaks a business rule or policy.

**Examples:**
- Trying to refund an order that is past the refund window
- Trying to book a room that is already reserved
- Discount code has expired

**Correct agent behavior:** Do not retry. Explain the situation to the user in a friendly way.

```json
{
  "isError": true,
  "errorCategory": "business",
  "isRetryable": false,
  "retryable": false,
  "message": "This order was placed 45 days ago. Refunds are only available within 30 days of purchase."
}
```

### 3.4 Permission Errors

**What they are:** The caller is not allowed to perform this action.

**Examples:**
- Missing API scope/permission
- User's account role does not allow this action
- Authentication token expired

**Correct agent behavior:** Do not retry with the same credentials. May need to ask a human to grant access, or re-authenticate.

```json
{
  "isError": true,
  "errorCategory": "permission",
  "isRetryable": false,
  "message": "This action requires 'admin' role. The current user has 'viewer' role."
}
```

### 3.5 Summary Table

| Category | Example Cause | Usually Retryable? | Agent Action |
|----------|----------------|---------------------|----------------|
| Transient | Timeout, service down | Yes | Retry, maybe with a short delay |
| Validation | Bad/missing input | No | Fix input, then retry |
| Business | Policy/rule violation | No | Explain to user, do not retry |
| Permission | Not authorized | No | Escalate or ask for correct access |

## 4. Why Uniform "Operation Failed" Messages Are a Problem

Imagine every error from every tool looks like this:

```json
{
  "isError": true,
  "content": [{ "type": "text", "text": "Operation failed." }]
}
```

This is called a **uniform error response**. It looks tidy, but it is actually harmful, because Claude cannot tell the difference between:

- A timeout that will likely succeed if retried
- Bad input that will always fail unless corrected
- A policy block that should never be retried
- A permission problem that needs a human to fix

### 4.1 What Goes Wrong Without Structured Errors

```
Tool fails → "Operation failed."
      │
      ▼
Claude doesn't know the cause
      │
      ├── Guesses "maybe retry" → wastes time/API calls on a validation error that will
      │                            never succeed no matter how many times it's retried
      │
      ├── Guesses "don't retry" → gives up on a simple timeout that would have
      │                            worked fine on the second try
      │
      └── Tells the user something vague and unhelpful
```

**Key idea:** A uniform error message removes the information Claude needs to make a *correct* recovery decision. Structured errors give Claude the details needed to react appropriately, every time.

## 5. Structured Error Metadata

To fix the uniform-error problem, every error response should include a consistent set of fields.

### 5.1 Minimum Recommended Fields

| Field | Type | Purpose |
|-------|------|---------|
| `isError` | boolean | Marks this result as a failure (MCP standard flag) |
| `errorCategory` | string | One of: `transient`, `validation`, `business`, `permission` |
| `isRetryable` | boolean | Tells Claude directly whether retrying makes sense |
| `message` | string | Human-readable explanation of what happened |

### 5.2 Full Example

```json
{
  "isError": true,
  "content": [
    { "type": "text", "text": "Refund request denied: outside the 30-day refund window." }
  ],
  "errorCategory": "business",
  "isRetryable": false,
  "message": "This order was placed 45 days ago. Our policy allows refunds only within 30 days of purchase. Please contact support if you believe this is an exception case."
}
```

Notice:
- `isRetryable: false` immediately tells Claude "don't try this again"
- `errorCategory: "business"` tells Claude this is a policy issue, not a bug
- The `message` is written so Claude can pass it along to the user directly — polite and clear, not a raw technical error

### 5.3 Business Errors Need Customer-Friendly Text

Since business errors are often shown directly to the end user, their `message` should be:
- Polite
- Clear about *why* the action was blocked
- Free of internal jargon or stack traces

**Bad:**
```json
{ "message": "Error code REFUND_ERR_402: window_exceeded" }
```

**Good:**
```json
{ "message": "This item's return window has closed. Returns are accepted within 30 days of delivery." }
```

## 6. Retryable vs Non-Retryable Errors

### 6.1 Why This Distinction Matters

If Claude does not know whether an error is retryable, it has two bad options:

1. **Retry everything** → wastes time and API calls on errors that will never succeed (like validation or permission errors)
2. **Retry nothing** → gives up on transient errors that would have worked fine a second time

The `isRetryable` boolean solves this by making the decision explicit, instead of something Claude has to guess.

### 6.2 Example Comparison

```json
// Transient — safe to retry
{
  "isError": true,
  "errorCategory": "transient",
  "isRetryable": true,
  "message": "Connection to inventory service timed out. Please retry."
}
```

```json
// Validation — retrying same input won't help
{
  "isError": true,
  "errorCategory": "validation",
  "isRetryable": false,
  "message": "Field 'email' is missing. Please supply a valid email address."
}
```

### 6.3 Decision Flow for Claude

```
Error received
      │
      ▼
Check isRetryable
      │
   ┌──┴──┐
  true   false
   │        │
   ▼        ▼
Retry     Do NOT retry
(maybe    Fix input, or
with a    explain to user,
short     or escalate
delay)    (based on errorCategory)
```

## 7. Local Error Recovery in Subagents

In multi-agent systems, a **subagent** may run a tool and hit a transient error. It does not always need to bother the **coordinator** (the higher-level agent managing the overall task) with every small hiccup.

### 7.1 The Pattern

1. Subagent calls a tool.
2. Tool returns a transient, retryable error.
3. Subagent retries locally (e.g., up to 2–3 times, maybe with a short wait between attempts).
4. **If it succeeds** → subagent continues normally, coordinator is never bothered.
5. **If it still fails after local retries** → subagent stops retrying and reports up to the coordinator, including:
   - What was attempted
   - Any partial results already gathered
   - The final structured error

### 7.2 Example: Subagent Handling a Transient Error Locally

```json
// Attempt 1 - fails
{ "isError": true, "errorCategory": "transient", "isRetryable": true, "message": "Timeout." }

// Subagent waits briefly and retries automatically (no need to tell coordinator yet)

// Attempt 2 - succeeds
{ "isError": false, "content": [{ "type": "text", "text": "Data retrieved successfully." }] }
```

The coordinator never even sees Attempt 1 — the subagent resolved it locally.

### 7.3 Example: Subagent Escalating After Local Recovery Fails

```json
{
  "escalatedError": {
    "isError": true,
    "errorCategory": "transient",
    "isRetryable": true,
    "message": "Inventory service still unavailable after 3 local retries."
  },
  "attempted": [
    "Called check_inventory tool 3 times over 15 seconds",
    "Confirmed network connectivity was fine"
  ],
  "partialResults": {
    "itemsChecked": ["SKU-001", "SKU-002"],
    "itemsRemaining": ["SKU-003"]
  }
}
```

Notice this escalation includes three important things:
1. The structured error itself
2. **What was attempted** before giving up
3. **Partial results** already gathered — so the coordinator does not have to start over from zero

### 7.4 Why This Pattern Matters

- It avoids flooding the coordinator with every minor transient hiccup
- Non-retryable errors (validation, business, permission) should typically be escalated right away — retrying locally will not help
- When escalating, always give the coordinator enough context (attempts + partial results) to make a good decision, instead of just "it failed"

### 7.5 Diagram: Local Recovery vs Escalation

```
Subagent runs tool
      │
      ▼
   Error occurs
      │
   ┌──┴─────────────────┐
   │                     │
transient/retryable   validation/business/permission
   │                     │
   ▼                     ▼
Retry locally        Escalate immediately
   │                 (retrying won't help)
   ├─ succeeds ──► continue, coordinator not bothered
   │
   └─ still fails after retries
          │
          ▼
     Escalate to coordinator
     with: error + attempted steps + partial results
```

## 8. Access Failures vs Valid Empty Results

This is a distinction that is easy to get wrong: **a query that finds nothing is not the same as a query that failed.**

### 8.1 Access Failure (a real error)

The tool could not even complete the search or action. Something went wrong on the way to getting an answer.

```json
{
  "isError": true,
  "errorCategory": "permission",
  "isRetryable": false,
  "message": "Access denied: you do not have permission to search this database."
}
```

### 8.2 Valid Empty Result (a success, just with no matches)

The tool worked correctly. It searched properly, and there simply was nothing matching the criteria.

```json
{
  "isError": false,
  "content": [
    { "type": "text", "text": "No orders found matching the given date range." }
  ],
  "results": []
}
```

### 8.3 Why Mixing These Up Is a Problem

If a valid empty result is incorrectly marked as an error:
- Claude might think something is broken and retry unnecessarily
- Claude might tell the user "there was a technical problem" when actually there is simply no data

If an access failure is incorrectly treated as a valid empty result:
- Claude might tell the user "no results found" when the real problem is that the search never actually happened
- The real issue (missing permissions, broken connection) goes unnoticed

### 8.4 Comparison Table

| Situation | isError | Meaning | Correct Agent Response |
|-----------|---------|---------|--------------------------|
| Search ran fine, 0 matches | `false` | Valid empty result | Tell user: "No results found" |
| Search could not run (auth/network/etc.) | `true` | Access failure | Tell user there was a problem; possibly retry or escalate depending on `errorCategory` |

## 9. Full Worked Example: A Well-Designed Tool Error Contract

Here is what a complete, well-structured error response looks like for a `check_order_status` tool, covering all the ideas in this tutorial:

```json
{
  "isError": true,
  "content": [
    { "type": "text", "text": "Unable to check order status: order ID not found." }
  ],
  "errorCategory": "validation",
  "isRetryable": false,
  "message": "No order was found with ID 'ORD-99999'. Please double check the order ID and try again.",
  "attempted": [
    "Looked up order ID 'ORD-99999' in the orders database"
  ]
}
```

And the corresponding success case, to show the contrast:

```json
{
  "isError": false,
  "content": [
    { "type": "text", "text": "Order ORD-12345 status: Shipped." }
  ],
  "results": {
    "orderId": "ORD-12345",
    "status": "Shipped"
  }
}
```

## 10. Quick Reference: Common Mistakes and Fixes

| Mistake | Why It's a Problem | Fix |
|---------|---------------------|-----|
| Generic "Operation failed" message | Claude can't decide whether to retry, fix input, or give up | Add `errorCategory`, `isRetryable`, and a clear `message` |
| No `isRetryable` flag | Claude may waste retries on errors that will never succeed | Always include `isRetryable: true/false` explicitly |
| Business errors with raw technical text | Confusing or unprofessional if shown to the user | Write `message` in polite, customer-friendly language |
| Subagent escalates every small transient error | Overloads the coordinator with noise | Recover locally first; escalate only if local retries fail |
| Escalating without context | Coordinator has to redo work from scratch | Always include what was attempted + any partial results |
| Empty result marked as an error | Claude may retry unnecessarily or alarm the user | Use `isError: false` with an empty `results` array for valid "no matches" cases |
| Real access failure marked as empty result | Hides a real problem (permissions, connectivity) | Use `isError: true` with the correct `errorCategory` for failures that prevented the search from completing |

---

## 11. Summary

- MCP tools use the `isError` flag to signal failure in a consistent, structured way.
- Errors fall into four categories: **transient**, **validation**, **business**, and **permission** — each needs different handling.
- Generic error messages like "Operation failed" prevent Claude from making good recovery decisions.
- Structured error metadata (`errorCategory`, `isRetryable`, `message`) tells Claude exactly what happened and what to do next.
- Business errors should include `retryable: false` and a customer-friendly explanation, since they are often shown directly to users.
- Subagents should try to recover from transient errors locally, and only escalate to the coordinator when local recovery fails — including what was attempted and any partial results.
- A valid empty result (search worked, found nothing) is very different from an access failure (search could not run) — always mark them differently so Claude and the user get the right message.
