# Domain 2: Tool Design & MCP Integration

## Task Statement 2.3: Distribute Tools Appropriately Across Agents and Configure Tool Choice

---

## 1. Introduction

When you build a system with multiple agents (a coordinator plus several subagents), a common mistake is giving every agent access to **every tool**. This feels convenient, but it actually makes the whole system less reliable.

In this tutorial, you will learn:

1. Why too many tools on one agent hurts tool selection
2. Why agents misuse tools outside their specialization
3. How to scope tool access by role
4. How to replace generic tools with constrained, purpose-built ones
5. How to give limited cross-role tools for common needs
6. How `tool_choice` works: `"auto"`, `"any"`, and forced tool selection
7. How to force a specific tool call as a first step, then continue in later turns

---

## 2. Too Many Tools Degrades Tool Selection Reliability

### 2.1 The Core Problem

Every time Claude needs to decide which tool to use, it must compare the user's request against **every available tool's description**. The more tools there are, the harder this comparison becomes — especially if some tools are similar to each other.

**Key idea:** Giving an agent 18 tools instead of 4-5 does not just add options — it increases decision complexity and makes wrong tool choices more likely, even if each individual tool description is well written.

### 2.2 Simple Analogy

Think of a toolbox. If a carpenter carries **only** a hammer, a saw, a tape measure, and a screwdriver, they can quickly grab the right one. If they carry **40 tools** for every possible job — plumbing, electrical, painting — they will take longer to choose, and may sometimes grab the wrong one, even for a simple task.

### 2.3 Diagram: Decision Complexity Grows with Tool Count

```
 Agent with 4 tools                    Agent with 18 tools
 ┌───────────────┐                     ┌───────────────────────────┐
 │ search_docs    │                    │ search_docs, fetch_url,    │
 │ summarize      │   Easy to match     │ summarize, translate,      │  Hard to match
 │ send_email     │   request → tool    │ send_email, send_sms,      │  request → tool
 │ create_ticket  │   quickly & well    │ create_ticket, schedule,   │  reliably
 └───────────────┘                     │ ...(11 more)...            │
                                        └───────────────────────────┘
```

### 2.4 Practical Guideline

- Keep each agent's tool list **small and focused** — a rough guideline used in practice is around **4-5 tools per agent**, not 15-20.
- If an agent seems to need many tools, that is often a sign the agent's role is too broad and should be split into more specialized agents (similar to splitting a generic tool, but at the agent level).

## 3. Why Agents Misuse Tools Outside Their Specialization

### 3.1 The Problem

When an agent has access to tools that are not related to its actual job, it will sometimes try to use them anyway — because the tool is *available*, even if it is not the *right* choice.

### 3.2 Example: A Synthesis Agent With a Web Search Tool

Imagine a **synthesis agent**. Its job is to combine information that has already been gathered by other agents into a final answer. It should not need to go find new information itself.

If this synthesis agent is given a `web_search` tool "just in case," it may start doing its own searches instead of just synthesizing what it was given — even when that is not its job.

```
Synthesis Agent's actual job:
   Take gathered research → combine into a clear final answer

Synthesis Agent's tools:
   [ combine_summaries, format_output, web_search ]  ← web_search doesn't belong here

Result:
   Agent sometimes does unnecessary web searches instead of
   simply synthesizing the material it already has, causing:
   - Slower responses
   - Duplicate or conflicting research
   - Unpredictable behavior
```

### 3.3 Why This Happens

- Claude selects tools based on what is available and what seems plausible for the request, not strictly what its "role" is supposed to be.
- If a tool is present, Claude may reason "this could help," even if the tool falls outside the agent's intended responsibility.

### 3.4 The Fix: Match Tools to Role

Give each agent **only** the tools that match its actual responsibility.

| Agent | Role | Tools It Should Have | Tools It Should NOT Have |
|-------|------|------------------------|-----------------------------|
| Research Agent | Finds raw information | `web_search`, `load_document` | `send_email`, `format_output` |
| Synthesis Agent | Combines findings into a final answer | `combine_summaries`, `format_output` | `web_search`, `fetch_url` |
| Notification Agent | Sends messages to users | `send_email`, `send_sms` | `web_search`, `combine_summaries` |

## 4. Scoped Tool Access

### 4.1 The Principle

**Scoped tool access** means: give each agent only the tools it truly needs for its role — not everything available in the system. If an agent occasionally needs a capability from another role, give it a **limited, specific version** of that tool rather than full access to another agent's whole toolkit.

### 4.2 Diagram: Scoped vs Unscoped Access

```
UNSCOPED (bad)                          SCOPED (good)
┌─────────────────────────┐             ┌───────────────────────────┐
│ Every agent has access   │             │ Coordinator                │
│ to every tool in the     │             │  └── has all tools         │
│ system                   │             │                             │
│                          │             │ Research Agent              │
│  Research Agent  ─┐      │             │  └── web_search,            │
│  Synthesis Agent ─┼──►[ALL TOOLS]      │      load_document          │
│  Notify Agent    ─┘      │             │                             │
└─────────────────────────┘             │ Synthesis Agent             │
                                          │  └── combine_summaries,     │
                                          │      format_output,         │
                                          │      verify_fact (scoped)   │
                                          │                             │
                                          │ Notify Agent                │
                                          │  └── send_email, send_sms   │
                                          └───────────────────────────┘
```

### 4.3 Why This Matters

- Reduces the chance of misuse (Section 3)
- Reduces decision complexity (Section 2)
- Makes each agent's behavior more predictable and easier to test
- Makes it easier to reason about security — an agent that cannot send emails, cannot accidentally send emails

## 5. Replacing Generic Tools with Constrained Alternatives

Sometimes the issue isn't which agent has a tool — it's that the tool itself is **too generic** and allows too much freedom, which invites misuse.

### 5.1 Example: `fetch_url` vs `load_document`

A generic `fetch_url` tool can retrieve **any** URL on the internet:

```json
{
  "name": "fetch_url",
  "description": "Fetches the contents of any URL."
}
```

This is risky and unpredictable because:
- It could be used to fetch unrelated or unapproved sites
- It has no built-in validation of what kind of content is expected
- It gives the agent very broad power for what might be a narrow task

A **constrained alternative**, `load_document`, limits what can be fetched and adds validation:

```json
{
  "name": "load_document",
  "description": "Loads a document from an approved internal document URL only (must start with 'https://docs.company.com/'). Rejects any other URL with a validation error. Use this to retrieve internal reports, not general web pages."
}
```

### 5.2 Why the Constrained Version Is Better

| `fetch_url` (generic) | `load_document` (constrained) |
|------------------------|----------------------------------|
| Accepts any URL | Only accepts approved document URLs |
| No validation | Validates URL pattern before running |
| Broad, unclear purpose | Narrow, clear purpose |
| Easy to misuse | Hard to misuse by design |

**Key idea:** Narrowing what a tool *can* do is often a better fix than just writing a better description for a tool that is inherently too powerful or too broad.

## 6. Scoped Cross-Role Tools for High-Frequency Needs

### 6.1 The Problem With "No Cross-Role Tools At All"

Strict scoping (Section 4) is good, but sometimes it is *too* strict. If a synthesis agent frequently needs to double-check a single fact, forcing it to always go through the coordinator for every tiny fact-check would be slow and inefficient.

### 6.2 The Solution: A Small, Scoped Cross-Role Tool

Instead of giving the synthesis agent the full research toolkit (like `web_search`, `load_document`, etc.), give it **one small, purpose-built tool** for that specific high-frequency need.

**Example: `verify_fact` for the Synthesis Agent**

```json
{
  "name": "verify_fact",
  "description": "Checks a single factual claim (max 1 sentence) against trusted reference sources and returns true/false with a short citation. Use this only to confirm a specific fact while synthesizing content. Do NOT use this for open-ended research — for broader research needs, escalate to the coordinator."
}
```

This tool:
- Does **one** narrow job (checking a single fact)
- Is much smaller in scope than a full research toolkit
- Reduces unnecessary round-trips to the coordinator for simple, frequent checks

### 6.3 Routing Complex Cases Through the Coordinator

For anything beyond this narrow scope — like needing to research a completely new topic — the synthesis agent should **not** try to do it itself. It should hand the task back to the coordinator, which can route it to the research agent.

```
Synthesis Agent needs to check something
        │
        ▼
   Is it a single, simple fact check?
        │
   ┌────┴────┐
  Yes        No
   │           │
   ▼           ▼
verify_fact   Escalate to Coordinator
(handles it    (Coordinator routes to
 directly)      Research Agent if needed)
```

### 6.4 Summary of the Pattern

| Situation | Correct Approach |
|-----------|--------------------|
| Synthesis agent needs to check one specific fact often | Give it a small scoped tool (`verify_fact`) |
| Synthesis agent needs broad new research | Route through the coordinator, not directly |
| Notification agent occasionally needs a document link | Consider a scoped tool, not full document search access |

## 7. `tool_choice` Configuration Options

`tool_choice` controls **how strongly** Claude is directed to use tools during a given turn. There are three main options.

### 7.1 `"auto"` (Default Behavior)

Claude decides on its own whether to use a tool, and if so, which one — based on the request and the available tool descriptions.

```json
{
  "tool_choice": { "type": "auto" }
}
```

**Use this when:** You want normal, flexible behavior — sometimes Claude should answer in plain text, sometimes it should call a tool, depending on the situation.

### 7.2 `"any"` (Force Some Tool Call)

Claude **must** call one of the available tools — it cannot simply respond with plain conversational text. It still chooses *which* tool, but it cannot choose "no tool."

```json
{
  "tool_choice": { "type": "any" }
}
```

**Use this when:** You want to guarantee that a tool gets used — for example, in a system where a plain text answer without checking a tool first would be incorrect or unsafe.

### 7.3 Forced Tool Selection (Specific Tool)

You specify the **exact tool name** Claude must call, removing all ambiguity about tool choice for this step.

```json
{
  "tool_choice": { "type": "tool", "name": "extract_metadata" }
}
```

**Use this when:** You need a specific tool to run first, in a specific order, before anything else happens — like validating input before any further processing occurs.

### 7.4 Comparison Table

| Option | Claude Can Respond With Plain Text? | Claude Chooses Which Tool? | Typical Use |
|--------|----------------------------------------|-------------------------------|----------------|
| `"auto"` | Yes | Yes | Normal, flexible conversations |
| `"any"` | No — must call a tool | Yes | Guarantee a tool is used, but flexible on which one |
| `{"type": "tool", "name": "..."}` | No — must call this tool | No — forced to one specific tool | Enforce a required first step |

## 8. Using Forced Tool Choice to Enforce Step Order

### 8.1 The Problem Without Forcing

Suppose you have a pipeline where a document must first go through `extract_metadata` before any enrichment tools (like `add_tags` or `summarize`) can safely run. If `tool_choice` is left as `"auto"`, Claude might call an enrichment tool first, working with incomplete information.

### 8.2 The Fix: Force the First Tool

**Step 1 — Force `extract_metadata` to run first:**

```json
{
  "tool_choice": { "type": "tool", "name": "extract_metadata" },
  "tools": ["extract_metadata", "add_tags", "summarize"]
}
```

This guarantees `extract_metadata` is the tool called in this turn — no other option is possible.

**Step 2 — In the follow-up turn, allow normal tool selection:**

After `extract_metadata` returns its result, the next turn can switch back to `"auto"` (or `"any"`, if a tool must still be used) so Claude can now correctly choose the right enrichment tool using the metadata it just extracted.

```json
{
  "tool_choice": { "type": "auto" },
  "tools": ["extract_metadata", "add_tags", "summarize"]
}
```

### 8.3 Diagram: Forced-Then-Free Tool Sequence

```
Turn 1: tool_choice = { "tool", "extract_metadata" }
        │
        ▼
   extract_metadata runs (guaranteed first step)
        │
        ▼
   Metadata result returned to Claude
        │
        ▼
Turn 2: tool_choice = "auto" (or "any")
        │
        ▼
   Claude now chooses the correct enrichment tool
   (add_tags, summarize, etc.) using the metadata
```

### 8.4 Why This Pattern Is Useful

- Ensures required steps always happen in the correct order
- Prevents Claude from skipping a necessary preparation step
- Still allows normal flexible tool selection for the steps that come after

## 9. Full Worked Example: Putting It All Together

Imagine a document-processing system with a coordinator and two subagents.

```
Coordinator
   │
   ├── Extraction Agent
   │      Tools: extract_metadata, load_document
   │      (scoped: only handles pulling data OUT of documents)
   │
   └── Enrichment Agent
          Tools: add_tags, summarize, verify_fact (scoped cross-role tool)
          (scoped: only handles improving/annotating already-extracted content)
```

**Step 1 — Coordinator forces the first tool:**
```json
{ "tool_choice": { "type": "tool", "name": "extract_metadata" } }
```

**Step 2 — Extraction Agent runs `extract_metadata`, returns structured metadata.**

**Step 3 — Coordinator hands off to the Enrichment Agent with `tool_choice: "auto"`**, letting it decide between `add_tags`, `summarize`, or a quick `verify_fact` check as needed — without ever needing (or being given) a broad `fetch_url` or `web_search` tool, because that is outside its scope.

**Step 4 — If the Enrichment Agent hits something beyond a simple fact check, it escalates to the Coordinator**, rather than trying to research it directly.

This example applies every idea in this tutorial:
- Small, focused tool lists per agent (Section 2)
- No unrelated tools given to agents outside their specialization (Section 3)
- Scoped access, with a small cross-role tool for high-frequency needs (Sections 4 & 6)
- A constrained tool (`load_document`) instead of a generic one (Section 5)
- Forced tool choice to guarantee order, then free choice afterward (Section 8)

## 10. Quick Reference: Common Mistakes and Fixes

| Mistake | Why It's a Problem | Fix |
|---------|---------------------|-----|
| Giving one agent 15-20 tools | Increases decision complexity, lowers selection reliability | Keep each agent's tool list small (roughly 4-5), split roles if needed |
| Giving agents tools outside their role | Agents may misuse tools that aren't meant for them | Scope tools strictly to each agent's actual responsibility |
| Using a generic `fetch_url`-style tool everywhere | Too broad, easy to misuse, no validation | Replace with a constrained, purpose-built tool (e.g. `load_document`) |
| No cross-role tools at all | Simple, frequent needs get routed through the coordinator every time, causing slowdowns | Provide a small scoped tool (e.g. `verify_fact`) for high-frequency cross-role needs |
| Leaving `tool_choice` as `"auto"` when a step is mandatory | Claude might skip or reorder a required step | Force the specific tool with `{"type": "tool", "name": "..."}` for that step |
| Never forcing tool use at all | Claude might respond with plain text when a tool call was actually required | Use `tool_choice: "any"` to guarantee a tool call when appropriate |

---

## 11. Summary

- Giving an agent too many tools (e.g., 18 instead of 4-5) increases decision complexity and lowers tool selection reliability.
- Agents tend to misuse tools that fall outside their specialization — for example, a synthesis agent trying to do its own web searches.
- Use **scoped tool access**: give each agent only the tools it needs for its role, with a small number of scoped cross-role tools for specific, high-frequency needs.
- Replace overly generic tools (like `fetch_url`) with constrained, purpose-built alternatives (like `load_document`) that validate their inputs.
- `tool_choice` has three modes: `"auto"` (Claude decides freely), `"any"` (Claude must call some tool), and forced selection (`{"type": "tool", "name": "..."}`, Claude must call one specific tool).
- Use forced tool selection to guarantee a required step happens first (e.g., `extract_metadata` before enrichment tools), then switch back to `"auto"` or `"any"` in the following turn for flexible tool use.
