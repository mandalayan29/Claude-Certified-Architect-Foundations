# Domain 2: Tool Design & MCP Integration

## Task Statement 2.1: Design Effective Tool Interfaces with Clear Descriptions and Boundaries

---

## 1. Introduction

When Claude works as an agent, it does not "guess" what a tool does by magic. Claude reads the **tool description** and decides which tool to use based on that text. This is why writing good tool descriptions is one of the most important skills when building agentic systems.

In this tutorial, you will learn:

1. Why tool descriptions matter so much
2. What good tool descriptions must include
3. How bad descriptions cause tool mix-ups (misrouting)
4. How system prompt wording affects tool choice
5. How to write, rename, and split tools to fix these problems

---

## 2. Why Tool Descriptions Are the Main Selection Mechanism

Claude does not see your code. Claude only sees:

- The tool **name**
- The tool **description**
- The tool's **input schema** (parameter names, types)

Based on this text alone, Claude must decide:

- Should I use a tool at all?
- Which tool, among many, fits this request?
- What values should I put in the parameters?

Think of tool descriptions like a **menu at a restaurant**. If the menu just says "Chicken Dish" and "Chicken Dish 2," you cannot tell what makes them different. You will pick randomly or ask questions. Claude behaves the same way with tools.

**Key idea:** A minimal or vague description does not just look untidy — it directly causes wrong tool selection, especially when there are multiple similar tools available.

### Simple Example of a Weak Description

```json
{
  "name": "get_data",
  "description": "Gets data.",
  "parameters": {
    "query": "string"
  }
}
```

This description tells Claude almost nothing:
- What kind of data?
- From where (database, web, file)?
- What format is `query` supposed to be in?

If there are two or three tools like this in the same system, Claude cannot reliably tell them apart.

## 3. What a Good Tool Description Must Include

A strong tool description answers four questions clearly:

| # | Question | What to Write |
|---|----------|----------------|
| 1 | What does this tool do? | A precise, specific purpose statement |
| 2 | What input does it expect? | Format, type, and an example |
| 3 | When should it be used vs NOT used? | Boundaries and comparison to similar tools |
| 4 | What are the edge cases? | Situations where behavior might surprise the caller |

### 3.1 Input Formats

Always describe the **exact shape** of the expected input. Don't just say "a string" — say what kind of string.

**Weak:**
```json
"description": "Searches using a query."
```

**Strong:**
```json
"description": "Searches the internal product catalog. Input must be a plain product name or SKU code (e.g. 'wireless mouse' or 'SKU-4521'). Do not pass full sentences or questions."
```

### 3.2 Example Queries

Adding one or two example inputs inside the description removes guesswork.

```json
{
  "name": "convert_currency",
  "description": "Converts an amount from one currency to another using live exchange rates. Example input: {\"amount\": 100, \"from\": \"USD\", \"to\": \"INR\"}. Use this only for currency conversion, not for stock prices or crypto."
}
```

### 3.3 Edge Cases

Tell Claude what happens in unusual situations, so it does not misuse the tool.

```
"Note: If the 'to' currency code is invalid, the tool returns an error object instead of a number. This tool does not support historical exchange rates — only the current rate."
```

### 3.4 Boundary Explanations

Boundaries tell Claude what the tool is **not** for. This is one of the most skipped parts of writing tool descriptions, and one of the most important.

```
"Use this tool only for weather forecasts up to 7 days ahead. Do NOT use this for historical weather data — use get_historical_weather instead."
```

### 3.5 Template You Can Reuse

```
This tool [does X specific action].
Input: [expected format + one example]
Output: [what is returned]
Use this when: [clear situation]
Do NOT use this when: [situation — point to the correct tool instead]
Edge cases: [what happens with bad/missing input]
```

## 4. How Ambiguous or Overlapping Descriptions Cause Misrouting

**Misrouting** means Claude picks the wrong tool for a task because two or more tool descriptions look too similar.

### 4.1 The Classic Example: `analyze_content` vs `analyze_document`

Imagine these two tools exist in the same system:

```json
[
  {
    "name": "analyze_content",
    "description": "Analyzes content and returns insights."
  },
  {
    "name": "analyze_document",
    "description": "Analyzes a document and returns insights."
  }
]
```

These descriptions are almost identical. The words "content" and "document" are the only difference, and both are vague. When a user asks:

> "Can you analyze this PDF report for key insights?"

Claude has no strong signal to pick one over the other. It may:
- Pick the wrong tool
- Alternate between tools inconsistently across similar requests
- Pass in the wrong kind of input (e.g., raw text into a tool built for file paths)

### 4.2 Why This Happens

- Both descriptions use the **same vague verbs** ("analyzes," "returns insights")
- Neither description says **what kind of input** it expects (web text? uploaded file? file path?)
- Neither description says **when to prefer one over the other**

### 4.3 Simple Diagram: Misrouting Flow

```
User Request: "Analyze this PDF report"
        │
        ▼
   Claude reads tool list
        │
        ├── analyze_content   (vague: "analyzes content")
        │
        └── analyze_document  (vague: "analyzes a document")
        │
        ▼
  Descriptions look almost the same
        │
        ▼
   Claude guesses -> may pick the WRONG tool
        │
        ▼
   Wrong tool runs -> wrong or failed output
```

Compare this with a system where descriptions are clear:

```
User Request: "Analyze this PDF report"
        │
        ▼
   Claude reads tool list
        │
        ├── extract_web_results  ("Use for URLs/web pages only")
        │
        └── summarize_pdf_document  ("Use for uploaded PDF/DOCX files only")
        │
        ▼
  Descriptions clearly separate use cases
        │
        ▼
   Claude picks the CORRECT tool confidently
        │
        ▼
   Correct output
```

## 5. Fixing Overlap: Renaming Tools and Rewriting Descriptions

One simple and powerful fix is to **rename** the tool so its name itself signals its purpose, and rewrite the description to be domain-specific.

### 5.1 Example Fix

**Before (ambiguous):**

```json
{
  "name": "analyze_content",
  "description": "Analyzes content and returns insights."
}
```

**After (renamed and clarified):**

```json
{
  "name": "extract_web_results",
  "description": "Extracts and summarizes key information from a live web page. Input must be a valid URL (e.g. 'https://example.com/article'). Use this only for content that comes from the internet. Do NOT use this for uploaded files — use summarize_pdf_document for that."
}
```

Notice what changed:
1. **Name** changed from generic (`analyze_content`) to specific (`extract_web_results`)
2. **Description** now states the exact input type (a URL)
3. **Description** now explicitly excludes the overlapping case and points to the correct alternative tool

### 5.2 Checklist for Renaming Tools

- [ ] Does the new name describe the action **and** the domain (e.g., `_web_`, `_pdf_`, `_database_`)?
- [ ] Does the description give one clear example input?
- [ ] Does the description explicitly say what NOT to use it for?
- [ ] If a similar tool exists, does the description point to it by name?

## 6. Fixing Overlap: Splitting Generic Tools

Sometimes the real problem is not the description — it's that **one tool is trying to do too many jobs**. The fix here is to **split** the tool into smaller, purpose-specific tools, each with its own clear input/output contract.

### 6.1 Example: Splitting `analyze_document`

A generic tool like this:

```json
{
  "name": "analyze_document",
  "description": "Analyzes a document."
}
```

...is actually being used for three very different jobs:
1. Pulling out specific numbers/facts
2. Writing a short summary
3. Checking if a claim is true against the source

Instead of one vague tool, split it into three specific tools:

```json
[
  {
    "name": "extract_data_points",
    "description": "Extracts specific numeric or factual data points from a document (e.g. dates, totals, names). Input: a document ID and a list of fields to extract, e.g. {\"doc_id\": \"123\", \"fields\": [\"total_revenue\", \"report_date\"]}. Output: a JSON object mapping each field to its found value. Use this when the user wants specific facts, not a general summary."
  },
  {
    "name": "summarize_content",
    "description": "Produces a short summary (3-5 sentences) of a document's overall content. Input: a document ID. Output: plain text summary. Use this when the user wants a general overview, not specific facts or verification."
  },
  {
    "name": "verify_claim_against_source",
    "description": "Checks whether a given claim/statement is supported by a specific document. Input: a document ID and a claim string, e.g. {\"doc_id\": \"123\", \"claim\": \"Revenue grew by 10% in 2024\"}. Output: {\"supported\": true/false, \"evidence\": \"...\"}. Use this only when the user explicitly wants fact-checking against a source, not for general summaries or data extraction."
  }
]
```

### 6.2 Why Splitting Helps

| Before (1 generic tool) | After (3 specific tools) |
|--------------------------|----------------------------|
| One vague purpose | Each tool has one clear job |
| Unclear what input to send | Each tool defines exact input |
| Unclear what comes back | Each tool defines exact output |
| Hard for Claude to pick correctly | Easy for Claude to match request to tool |

### 6.3 Diagram: Splitting a Generic Tool

```
                 analyze_document (generic, unclear)
                            │
        ┌───────────────────┼───────────────────┐
        ▼                   ▼                   ▼
extract_data_points   summarize_content   verify_claim_against_source
 (facts/numbers)         (overview)           (fact-check)
```

**Rule of thumb:** If you find yourself writing "and/or" many times in one tool's description, that tool is probably doing too much and should be split.

## 7. How System Prompt Wording Affects Tool Selection

Even with perfectly written tool descriptions, the **system prompt** can still cause problems. This happens because certain words in the system prompt make Claude more likely to associate a task with a specific tool — even when that tool is not the best fit. This is called being **keyword-sensitive**.

### 7.1 Example of the Problem

Suppose the system prompt says:

```
"Always analyze any document the user shares to check for key information."
```

Now, if there are two tools — `summarize_content` and `extract_data_points` — the word **"analyze"** in the system prompt might unintentionally pull Claude toward whichever tool description also contains the word "analyze," even if `extract_data_points` (which doesn't use that word) is the better fit for a specific request.

### 7.2 Why This Happens

- System prompt instructions carry strong weight in Claude's decision-making
- If a system prompt repeats a keyword (like "analyze," "search," "check") that also appears in one tool's description more than another, Claude may lean toward that tool out of habit, even when it's not the best match
- This creates an **unintended association** between a general instruction and a specific tool

### 7.3 How to Review System Prompts for This Issue

When reviewing a system prompt, ask:

1. **Does the system prompt use a specific action word repeatedly** (e.g., "always analyze," "always search")?
2. **Does that same word appear in only one tool's name or description**, even though multiple tools could apply?
3. **Would a neutral, general instruction work instead** ("review the user's request and choose the most specific matching tool")?

### 7.4 Before and After Example

**Before (keyword-sensitive, biased toward one tool):**
```
System Prompt: "Always analyze user-provided content thoroughly before responding."
Tools available: analyze_content, extract_data_points, summarize_content, verify_claim_against_source
```
Here, "analyze" strongly matches `analyze_content` by name, even if the user actually wants a summary or fact extraction.

**After (neutral wording, description-driven selection):**
```
System Prompt: "Review the user's request and select the single tool whose description most specifically matches the task. Do not default to any one tool."
```
This removes the keyword bias and lets the tool descriptions (which you already wrote clearly) do their job properly.

## 8. Full Worked Example: Before and After

### Before: Problem System

```json
{
  "system_prompt": "Always analyze any file or content the user provides.",
  "tools": [
    { "name": "analyze_content", "description": "Analyzes content and returns insights." },
    { "name": "analyze_document", "description": "Analyzes a document and returns insights." }
  ]
}
```

**Problems:**
- Two tools with near-identical descriptions
- No input format specified
- No boundary between them
- System prompt repeats "analyze," biasing tool choice

### After: Fixed System

```json
{
  "system_prompt": "Review the user's request and select the tool whose description most specifically matches the input type and goal.",
  "tools": [
    {
      "name": "extract_web_results",
      "description": "Extracts key information from a live web page. Input: a URL. Use only for internet content, not uploaded files."
    },
    {
      "name": "extract_data_points",
      "description": "Extracts specific facts/numbers from an uploaded document. Input: doc_id + list of fields. Use when the user wants specific data, not a summary."
    },
    {
      "name": "summarize_content",
      "description": "Produces a short summary of an uploaded document. Input: doc_id. Use for general overviews only."
    },
    {
      "name": "verify_claim_against_source",
      "description": "Checks if a claim is supported by an uploaded document. Input: doc_id + claim text. Use only for fact-checking requests."
    }
  ]
}
```

**Fixes applied:**
1. Tool names now describe both the action and the domain
2. Every description includes input format
3. Every description states its boundary ("use only for...")
4. The generic `analyze_document` was split into three purpose-specific tools
5. The system prompt was reworded to remove keyword bias

## 9. Quick Reference: Common Mistakes and Fixes

| Mistake | Why It's a Problem | Fix |
|---------|---------------------|-----|
| Vague verbs ("analyzes," "processes," "handles") | Doesn't tell Claude what actually happens | Use specific action verbs tied to the exact task |
| No input format or example | Claude may send wrong data shape | Add expected format + one example input |
| No boundary statement | Claude can't tell this tool apart from similar ones | Add "Use this only for..." / "Do NOT use for..." |
| Two tools doing similar jobs | Causes misrouting | Rename or split into purpose-specific tools |
| One tool doing many jobs | Description becomes vague trying to cover everything | Split into focused tools with clear input/output |
| System prompt repeats one keyword | Creates bias toward one tool | Use neutral instructions describing the *process* of selection, not a specific action word |

---

## 10. Summary

- Claude picks tools mainly by reading their **descriptions** — vague descriptions lead to unreliable choices.
- Good descriptions include: **purpose, input format, example, output, when to use, when not to use, and edge cases**.
- Similar tools with near-identical descriptions (like `analyze_content` vs `analyze_document`) cause **misrouting**.
- Fix overlap by **renaming** tools to be domain-specific and rewriting descriptions with clear boundaries.
- Fix overly generic tools by **splitting** them into smaller tools, each with its own input/output contract.
- Always **review the system prompt** for repeated keywords that might quietly bias Claude toward one tool over another — even if your tool descriptions are well written.
