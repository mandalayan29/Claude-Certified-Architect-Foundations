## 1. Introduction

MCP (Model Context Protocol) servers give Claude access to external tools, data, and systems — things like GitHub, Jira, databases, or internal company systems. But *where* and *how* you configure an MCP server matters a lot.

In this tutorial, you will learn:

1. The two levels of MCP server scoping: project-level vs user-level
2. How to safely manage credentials using environment variable expansion
3. How tools from multiple MCP servers become available to Claude
4. How MCP **resources** help agents avoid unnecessary exploratory tool calls
5. How to write MCP tool descriptions that stop Claude from preferring built-in tools instead
6. When to use an existing community MCP server vs building a custom one
7. How to expose content catalogs as MCP resources

## 2. MCP Server Scoping: Project-Level vs User-Level

MCP servers can be configured at two different levels, depending on **who should have access** to them.

### 2.1 Project-Level Scoping: `.mcp.json`

A `.mcp.json` file lives inside a project's folder. It is meant for **shared team tooling** — servers that everyone working on this project should have access to, like a shared GitHub integration or an internal ticketing system.

**Key idea:** Because `.mcp.json` lives in the project folder, it can be checked into version control (like Git) and shared with the whole team, so everyone gets the same tools automatically when they open the project.

```json
{
  "mcpServers": {
    "github": {
      "command": "npx",
      "args": ["-y", "@modelcontextprotocol/server-github"],
      "env": {
        "GITHUB_TOKEN": "${GITHUB_TOKEN}"
      }
    }
  }
}
```

### 2.2 User-Level Scoping: `~/.claude.json`

`~/.claude.json` lives in the user's home directory, not inside any specific project. It is meant for **personal or experimental servers** — tools that only *you* want available, across any project you work on, such as a personal note-taking tool or a server you are still testing.

```json
{
  "mcpServers": {
    "my_personal_notes": {
      "command": "node",
      "args": ["/Users/me/tools/notes-server/index.js"]
    }
  }
}
```

### 2.3 Comparison Table

| Aspect | Project-Level (`.mcp.json`) | User-Level (`~/.claude.json`) |
|--------|-------------------------------|-----------------------------------|
| Location | Inside the project folder | In the user's home directory |
| Who sees it | Whole team (if committed to version control) | Only you |
| Best for | Shared, team-wide tools (e.g. company GitHub, Jira) | Personal or experimental tools |
| Typical content | Stable, agreed-upon integrations | Servers you're still testing out |

### 2.4 Diagram: Scoping Overview

```
Project Folder
 ├── .mcp.json          ──► shared with the whole team (via version control)
 │                            e.g. github, jira, internal-docs
 │
User's Home Directory
 └── ~/.claude.json      ──► personal to this user only
                              e.g. my_experimental_server, personal_notes
```

**Rule of thumb:** If every teammate working on this project should have this tool, put it in `.mcp.json`. If it's just for you, or still experimental, put it in `~/.claude.json`.

## 3. Environment Variable Expansion for Credential Management

### 3.1 The Problem

MCP servers often need credentials — API tokens, keys, passwords — to connect to external services. You should **never** write these secrets directly into a file that might get committed to version control (like `.mcp.json`), because that would expose them to anyone who can see the repository.

### 3.2 The Solution: `${VARIABLE_NAME}` Expansion

Instead of hardcoding a secret, `.mcp.json` supports **environment variable expansion**. You reference the variable name, and the actual value is filled in at runtime from the environment — never written into the file itself.

```json
{
  "mcpServers": {
    "github": {
      "command": "npx",
      "args": ["-y", "@modelcontextprotocol/server-github"],
      "env": {
        "GITHUB_TOKEN": "${GITHUB_TOKEN}"
      }
    }
  }
}
```

Here, `${GITHUB_TOKEN}` is **not** the actual token — it is a placeholder that gets replaced with the real value from the user's local environment variable of the same name, when the server actually starts.

### 3.3 Why This Matters

- The `.mcp.json` file can be safely committed to Git and shared with the team
- Each teammate can have their **own** personal token set locally, without needing to share it with anyone
- If a token needs to be rotated or changed, you only update the environment variable — not the shared config file

### 3.4 Diagram: How Expansion Works

```
.mcp.json (safe to share)
  "GITHUB_TOKEN": "${GITHUB_TOKEN}"
        │
        ▼
 At runtime, looks up GITHUB_TOKEN
 from the local machine's environment
        │
        ▼
 Local environment variable (never committed)
  GITHUB_TOKEN=ghp_xxxxxxxxxxxx
        │
        ▼
 Real token value is used to start the server
```

## 4. Tools from All Configured MCP Servers Are Available Simultaneously

### 4.1 The Key Fact

When Claude Code connects, it discovers the tools from **every configured MCP server** — both project-level and user-level — at connection time. All of these tools become available to the agent **at the same time**, in the same conversation.

```
Connection Time
      │
      ▼
Discover tools from .mcp.json servers   (e.g., github, jira)
      +
Discover tools from ~/.claude.json servers   (e.g., personal_notes)
      │
      ▼
All discovered tools are now available together
to the agent in this session
```

### 4.2 Why This Matters

Since tools from **all** servers are combined into one big pool, this connects directly back to earlier lessons in this domain:

- If too many servers are connected at once, the agent can end up with a very large combined tool list — which, as covered in Task Statement 2.3, **degrades tool selection reliability**.
- Overlapping or similarly-named tools from *different* servers can cause the same kind of **misrouting** problems covered in Task Statement 2.1.

**Practical takeaway:** Be deliberate about which MCP servers you connect for a given project or session — don't just enable everything "in case it's useful."

## 5. MCP Resources: Reducing Exploratory Tool Calls

### 5.1 The Problem Without Resources

Without any upfront information, an agent that wants to understand what data is available often has to make **exploratory tool calls** — calling a tool just to find out what exists, before it can call another tool to actually do the real work.

**Example (inefficient):**
```
Agent wants to find "the schema of the orders table"
      │
      ▼
Call list_tables tool          ──► finds table names
      │
      ▼
Call describe_table("orders")  ──► finally gets the schema
```

This costs extra tool calls just to *discover* information that could have been made visible from the start.

### 5.2 The Solution: MCP Resources

**MCP resources** let a server expose a **catalog of content** directly — like a list of issue summaries, a documentation hierarchy, or a database schema — so the agent can see what's available **without** having to call a tool first just to explore.

### 5.3 Examples of Content Catalogs as Resources

| Type of Resource | What It Exposes | Saves the Agent From |
|---------------------|--------------------|---------------------------|
| Issue summaries | A list of current tickets/issues with short descriptions | Calling `list_issues` repeatedly just to browse |
| Documentation hierarchy | A tree of available docs/pages | Calling `search_docs` blindly to see what topics exist |
| Database schema | Table names, column names, and types | Calling `describe_table` for every table one by one |

### 5.4 Diagram: With vs Without Resources

```
WITHOUT RESOURCES (more tool calls)          WITH RESOURCES (fewer tool calls)
Agent needs schema info                       Agent needs schema info
      │                                              │
      ▼                                              ▼
 Call list_tables                             Reads schema directly
      │                                        from an exposed MCP resource
      ▼                                              │
 Call describe_table (x N tables)                    ▼
      │                                        Already has what it needs —
      ▼                                        no exploratory calls required
 Finally has schema info
```

### 5.5 Why This Matters

- Fewer wasted tool calls means faster responses and lower cost
- The agent has a clearer "map" of what is available before deciding what to do
- Reduces the chance of the agent guessing incorrectly about what data exists

## 6. Writing MCP Tool Descriptions That Prevent Built-In Tool Preference

### 6.1 The Problem

Claude Code has certain **built-in tools** available by default, such as a `Grep`-style search tool for searching text/files. If an MCP tool's description is too short or vague, Claude may default to using the familiar built-in tool instead — even when the MCP tool would actually do a much better, more capable job.

### 6.2 Example: Weak MCP Tool Description

```json
{
  "name": "search_codebase",
  "description": "Searches the codebase."
}
```

This looks like it does the same thing as a simple built-in text search (`Grep`). Claude has no reason to prefer it, so it may just use the built-in `Grep` tool instead — even if `search_codebase` actually understands code structure, symbols, and cross-file references far better than a plain text search would.

### 6.3 Example: Strong MCP Tool Description

```json
{
  "name": "search_codebase",
  "description": "Performs a semantic, structure-aware search across the entire codebase, understanding function/class relationships and cross-file references — unlike a plain text search. Use this instead of a basic grep/text search whenever the user asks about how something is used, defined, or connected across files. Input: a natural-language question or a symbol name. Output: ranked list of relevant code locations with context."
}
```

This description clearly explains:
- What makes it more capable than a basic text search
- That it should be preferred **over** the built-in text search tool for this kind of task
- What input it expects, and what it returns

### 6.4 Key Principle

**Detailed, specific tool descriptions are what stop Claude from defaulting to a familiar built-in tool.** If an MCP tool's description doesn't clearly explain *why* it's better for a given task, Claude has no strong reason to choose it over something it already knows how to use.

## 7. Choosing Existing Community MCP Servers vs Building Custom Ones

### 7.1 The General Rule

For **standard integrations** — well-known systems like Jira, GitHub, Slack, or similar common tools — prefer using an **existing, well-maintained community MCP server** instead of building your own from scratch.

### 7.2 Why Prefer Existing Servers for Standard Integrations

- Community servers are already tested by many other users
- They are usually kept up to date with API changes from the underlying service
- Building your own means maintaining it forever, including fixing bugs and adjusting to future API changes

### 7.3 When a Custom Server Makes Sense

Build a **custom MCP server** when the workflow is specific to your team or organization — something a generic community server could never cover, because it depends on your own internal systems, data, or business rules.

**Examples of team-specific workflows worth a custom server:**
- Querying your company's internal customer database with your specific schema
- A tool that applies your team's specific approval workflow before an action is taken
- Integrating with an internal-only system that has no public API or community support

### 7.4 Decision Table

| Situation | Recommended Approach |
|-----------|--------------------------|
| Need to integrate with Jira, GitHub, Slack, etc. (standard/common) | Use an existing community MCP server |
| Need to integrate with an internal, company-specific database or workflow | Build a custom MCP server |
| A community server exists but is missing one small feature you need | Consider contributing to it, before building a whole custom server from scratch |

### 7.5 Diagram: Decision Flow

```
Need an MCP integration
        │
        ▼
Is this a standard, well-known service (Jira, GitHub, Slack, etc.)?
        │
   ┌────┴────┐
  Yes         No
   │           │
   ▼           ▼
Use an       Is it a team-specific workflow
existing     or internal-only system?
community        │
server           ▼
              Build a custom MCP server
```

## 8. Exposing Content Catalogs as MCP Resources — Practical Example

Let's put together a full example: an internal documentation MCP server for a team.

### 8.1 Without a Resource (Tool-Only Approach)

```json
{
  "name": "search_docs",
  "description": "Searches internal documentation by keyword."
}
```

Every time the agent wants to know what documentation topics even exist, it has to call `search_docs` with a guess and see what comes back — pure trial and error.

### 8.2 With a Resource (Catalog Exposed Upfront)

The server can additionally expose a **resource** representing the documentation hierarchy:

```json
{
  "resource": {
    "uri": "docs://hierarchy",
    "name": "Documentation Hierarchy",
    "description": "A tree of all available internal documentation pages, organized by category.",
    "mimeType": "application/json"
  }
}
```

When the agent reads this resource, it might see something like:

```json
{
  "Engineering": ["Deployment Guide", "API Reference", "Coding Standards"],
  "HR": ["Leave Policy", "Onboarding Checklist"],
  "Sales": ["Pricing Sheet", "Discount Approval Process"]
}
```

Now the agent already knows what topics exist **before** making any search calls, and can go straight to `search_docs` with a much more precise, targeted query — instead of guessing blindly.

### 8.3 Diagram: Full Flow With Resource + Tool Together

```
Agent needs info about "Discount Approval Process"
        │
        ▼
Reads exposed resource: docs://hierarchy
        │
        ▼
Sees "Sales" category includes "Discount Approval Process"
        │
        ▼
Calls search_docs("Discount Approval Process") directly
        │
        ▼
Gets exact, relevant content — no wasted exploratory calls
```

## 9. Full Worked Example: Setting Up an MCP Integration for a Team

Imagine a team wants to add both a shared GitHub integration and a personal experimental server.

**`.mcp.json` (project-level, committed to Git):**
```json
{
  "mcpServers": {
    "github": {
      "command": "npx",
      "args": ["-y", "@modelcontextprotocol/server-github"],
      "env": {
        "GITHUB_TOKEN": "${GITHUB_TOKEN}"
      }
    },
    "jira": {
      "command": "npx",
      "args": ["-y", "@modelcontextprotocol/server-jira"],
      "env": {
        "JIRA_API_TOKEN": "${JIRA_API_TOKEN}"
      }
    }
  }
}
```

- Both `github` and `jira` are **existing community servers** for standard integrations (Section 7)
- Both use `${...}` environment variable expansion so no secrets are exposed in the file (Section 3)
- This file is safe to commit and share with the whole team (Section 2)

**`~/.claude.json` (user-level, personal only):**
```json
{
  "mcpServers": {
    "my_experimental_search": {
      "command": "node",
      "args": ["/Users/me/experiments/search-server/index.js"]
    }
  }
}
```

- This is a personal, experimental server, not something the whole team needs yet (Section 2)
- It stays local to this one developer's machine

At connection time, this developer will have tools from **all three** servers (`github`, `jira`, `my_experimental_search`) available simultaneously (Section 4) — so the team should be mindful of how many servers get connected at once, to avoid overloading the agent's tool selection (linking back to Task Statement 2.3).

## 10. Quick Reference: Common Mistakes and Fixes

| Mistake | Why It's a Problem | Fix |
|---------|---------------------|-----|
| Putting personal/experimental servers in `.mcp.json` | Forces experimental tools on the whole team | Use `~/.claude.json` for personal or experimental servers |
| Hardcoding API tokens directly in `.mcp.json` | Secrets get exposed if the file is committed to version control | Use `${VARIABLE_NAME}` environment variable expansion instead |
| Connecting many MCP servers "just in case" | Combined tool list grows large, hurting tool selection reliability | Only connect servers actually needed for the current project/session |
| Vague MCP tool descriptions | Claude defaults to familiar built-in tools (like `Grep`) instead of a more capable MCP tool | Write detailed descriptions explaining why/when the MCP tool is better |
| Building a custom MCP server for a standard service | Extra unnecessary maintenance burden | Use an existing, well-maintained community server instead |
| No resources exposed for browsable data | Agent wastes tool calls exploring blindly | Expose a content catalog (issues, docs, schema) as an MCP resource |

---

## 11. Summary

- MCP servers can be scoped at the **project level** (`.mcp.json`, shared with the team) or the **user level** (`~/.claude.json`, personal/experimental).
- Use **environment variable expansion** (e.g. `${GITHUB_TOKEN}`) in `.mcp.json` so credentials are never hardcoded or committed to version control.
- Tools from **all** configured MCP servers — project and user level — are discovered at connection time and become available to the agent **simultaneously**, so connect servers deliberately.
- **MCP resources** expose content catalogs (issue summaries, documentation hierarchies, database schemas) so agents can see what's available without wasting exploratory tool calls.
- Write **detailed** MCP tool descriptions that explain their advantages, so Claude doesn't default to a familiar built-in tool (like `Grep`) when the MCP tool is actually more capable.
- Prefer **existing community MCP servers** for standard integrations (Jira, GitHub, Slack), and reserve **custom servers** for workflows that are specific to your team or organization.
