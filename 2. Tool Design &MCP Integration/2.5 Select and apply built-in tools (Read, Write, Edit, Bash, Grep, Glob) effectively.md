# Domain 2: Tool Design & MCP Integration

## Task Statement 2.5: Select and Apply Built-in Tools (Read, Write, Edit, Bash, Grep, Glob) Effectively

---

## 1. Introduction

Claude Code comes with a set of **built-in tools** for working with code and files. Knowing which tool to reach for — and when — is a core skill for working efficiently in a codebase.

In this tutorial, you will learn:

1. What each built-in tool is for: `Grep`, `Glob`, `Read`, `Write`, `Edit`, `Bash`
2. When to use `Grep` vs `Glob`
3. The difference between `Read`/`Write` (full file) and `Edit` (targeted change)
4. What to do when `Edit` fails because of non-unique text matches
5. How to explore a codebase incrementally instead of reading everything upfront
6. How to trace a function's usage across wrapper modules

---

## 2. Overview of the Built-in Tools

| Tool | Purpose | Works On |
|------|---------|----------|
| `Grep` | Searches file **contents** for a text pattern | Text inside files |
| `Glob` | Finds files by **name/path pattern** | File names and paths |
| `Read` | Loads the **full contents** of a file | One file at a time |
| `Write` | Writes/overwrites the **full contents** of a file | One file at a time |
| `Edit` | Makes a **targeted change** inside a file, using unique text matching | One file at a time |
| `Bash` | Runs shell commands (e.g. running tests, installing packages, git commands) | The system/terminal |

**Simple way to remember it:**
- `Grep` = "What's written **inside** the files?"
- `Glob` = "**Which** files even exist, based on their names?"
- `Read`/`Write` = "Give me the **whole** file / replace the **whole** file"
- `Edit` = "Change **just this one part** of the file"
- `Bash` = "Run a **command**, not just look at files"

## 3. `Grep`: Searching File Contents

### 3.1 What It's For

`Grep` searches **inside** files for a text pattern. Use it when you know roughly **what text** you're looking for, but not necessarily which file it's in.

### 3.2 Typical Use Cases

- Finding all the places a function is called
- Locating a specific error message in logs or code
- Finding all files that import a certain module
- Searching for a specific string, like a config key or environment variable name

### 3.3 Example

```bash
# Find every place that calls the function "calculateDiscount"
Grep pattern: "calculateDiscount\("
```

```bash
# Find every file that imports a specific module
Grep pattern: "from ['\"]utils/logger['\"]"
```

```bash
# Find where a specific error message is thrown
Grep pattern: "Order not found"
```

### 3.4 When to Reach for `Grep`

> "I know what text I'm looking for, but I don't know which file(s) it's in."

---

## 4. `Glob`: Finding Files by Name Pattern

### 4.1 What It's For

`Glob` finds files based on their **name or path pattern** — not their content. Use it when you know something about the **file name or extension**, but not necessarily what's inside.

### 4.2 Typical Use Cases

- Finding all test files
- Finding all files of a certain type (e.g. all `.tsx` files)
- Finding all files inside a specific folder structure

### 4.3 Example

```bash
# Find all test files, no matter which folder they're in
Glob pattern: "**/*.test.tsx"
```

```bash
# Find all Python files in a "services" folder
Glob pattern: "services/**/*.py"
```

```bash
# Find all Markdown files at the top level only
Glob pattern: "*.md"
```

### 4.4 When to Reach for `Glob`

> "I know something about the file **name/type/location**, but I don't need to search inside file contents yet."

### 4.5 `Grep` vs `Glob` Quick Comparison

| Question You're Asking | Right Tool |
|--------------------------|--------------|
| "Which files call this function?" | `Grep` |
| "Which files are test files?" | `Glob` |
| "Where does this error message come from?" | `Grep` |
| "What are all the `.env` files in this repo?" | `Glob` |

## 5. `Read` and `Write`: Full File Operations

### 5.1 `Read`

`Read` loads the **entire contents** of one file so Claude can see everything in it.

**Use `Read` when:**
- You need to see the full context of a file, not just a fragment
- You are about to make a change and need to understand the surrounding code first
- You are following an import to see what a module actually contains

### 5.2 `Write`

`Write` creates a new file or **completely replaces** the contents of an existing file.

**Use `Write` when:**
- Creating a brand-new file
- Fully rewriting a file (not just changing one small part)
- As a fallback after `Edit` fails (covered in Section 7)

### 5.3 Example

```bash
# Read the full contents of a config file before editing it
Read: "src/config/settings.py"
```

```bash
# Write a brand-new file
Write: "src/utils/formatDate.js"
Content: "export function formatDate(date) { ... }"
```

## 6. `Edit`: Targeted Modifications Using Unique Text Matching

### 6.1 What It's For

`Edit` changes **just one specific part** of a file, without touching the rest. It works by matching a **unique piece of existing text** in the file, and replacing it with new text.

### 6.2 Example

```bash
Edit file: "src/utils/math.js"
Old text: "function add(a, b) { return a + b; }"
New text: "function add(a, b) { return Number(a) + Number(b); }"
```

Because `"function add(a, b) { return a + b; }"` appears **only once** in the file, `Edit` can confidently find and replace exactly that spot, leaving everything else untouched.

### 6.3 Why `Edit` Requires Uniqueness

`Edit` needs the "old text" to match **exactly one location** in the file. If the exact same text appears in **more than one place**, `Edit` cannot know which one you meant to change — so it fails, rather than guessing and possibly changing the wrong spot.

### 6.4 When to Reach for `Edit`

> "I want to change one small, specific part of a file, and I can point to unique surrounding text."

---

## 7. When `Edit` Fails: Non-Unique Text Matches

### 7.1 The Problem

Suppose a file has this pattern appearing **twice**:

```javascript
// Appears at line 10
if (status === "pending") {
  return false;
}

// Appears again at line 47
if (status === "pending") {
  return false;
}
```

If you try to `Edit` using `"if (status === \"pending\") { return false; }"` as the old text, `Edit` will fail — because it cannot tell which of the two matches you actually meant to change.

### 7.2 The Fallback: `Read` + `Write`

When `Edit` fails due to a non-unique match, the reliable fallback is:

1. **`Read`** the full file to see all the surrounding context
2. Manually construct the **entire updated file content**, with the correct change made in the correct place
3. **`Write`** the full updated content back to the file

### 7.3 Diagram: Edit Failure and Fallback Flow

```
Try Edit with target text
         │
         ▼
   Is the text unique in the file?
         │
    ┌────┴────┐
   Yes         No (matches found in multiple places)
    │             │
    ▼             ▼
 Edit succeeds   Edit fails
    │             │
    ▼             ▼
 Done          Fallback:
                 1. Read full file
                 2. Build the complete corrected content
                 3. Write the full file back
```

### 7.4 Example of the Fallback in Action

```bash
# Step 1: Read the full file to see both occurrences and their context
Read: "src/handlers/orderStatus.js"

# Step 2: Claude studies the surrounding lines to tell the two occurrences apart
#          (e.g., one is inside `checkShipping()`, the other inside `checkPayment()`)

# Step 3: Write the complete file back, with only the correct occurrence changed
Write: "src/handlers/orderStatus.js"
Content: "...(full file, with just the intended line updated)..."
```

### 7.5 Key Principle

**`Edit` is preferred when possible**, because it is precise and only touches what's necessary. But when `Edit` cannot find a unique anchor, `Read` + `Write` is the reliable fallback — it lets Claude see the full picture and make sure the *correct* occurrence is changed, not a guess.

## 8. `Bash`: Running Commands

### 8.1 What It's For

`Bash` runs shell commands — this goes beyond just reading or editing files. Use it for actions like running tests, installing dependencies, or using git.

### 8.2 Example

```bash
# Run the test suite
Bash: "npm test"
```

```bash
# Check git status before committing
Bash: "git status"
```

```bash
# Install a new dependency
Bash: "pip install requests"
```

### 8.3 When to Reach for `Bash`

> "I need to actually **run** something (a command, a script, a test), not just look at or change a file."

## 9. Building Codebase Understanding Incrementally

### 9.1 The Problem With Reading Everything Upfront

A common mistake is trying to `Read` every file in a codebase before doing anything else. This is slow, wastes a huge amount of context, and is usually unnecessary — most of those files won't even be relevant to the task at hand.

### 9.2 The Better Approach: Start Narrow, Expand as Needed

1. **Start with `Grep`** to find entry points — for example, search for a function name, an error message, or a specific keyword related to the task
2. **Use `Read`** to open just the specific files that `Grep` pointed to
3. **Follow imports** from those files — if a file imports something relevant, `Read` that next
4. Repeat, expanding your understanding **only as needed**, instead of loading the whole codebase at once

### 9.3 Diagram: Incremental Exploration

```
Task: "Fix a bug in how discounts are calculated"
        │
        ▼
Step 1: Grep for "calculateDiscount" across the codebase
        │
        ▼
Step 2: Grep results show it's defined in pricing/discount.js
        │
        ▼
Step 3: Read pricing/discount.js to understand the function
        │
        ▼
Step 4: That file imports "taxRules" from pricing/tax.js
        │
        ▼
Step 5: Read pricing/tax.js only because it was actually relevant
        │
        ▼
Now Claude has just enough context to make the fix —
without reading unrelated files across the whole project
```

### 9.4 Why This Matters

- Saves time and context space
- Keeps focus on what's actually relevant to the task
- Mirrors how a human developer would naturally explore unfamiliar code — starting from a clue, then following the thread

## 10. Tracing Function Usage Across Wrapper Modules

### 10.1 The Problem

Sometimes a function is not called directly — it's **wrapped** or **re-exported** by another module under a different name. If you only search for the original function name, you might miss many of its real usages.

### 10.2 Example of the Problem

```javascript
// pricing/discount.js
export function calculateDiscount(price) { ... }
```

```javascript
// pricing/index.js  (a wrapper module)
export { calculateDiscount as getDiscount } from './discount.js';
```

If you only `Grep` for `"calculateDiscount"`, you will **miss** every place in the codebase that imports and calls it as `getDiscount` instead.

### 10.3 The Correct Approach: Identify All Exported Names First

1. **`Read`** the original module and any wrapper/index modules that re-export the function
2. **Identify every name** the function is exported as (e.g. `calculateDiscount`, `getDiscount`)
3. **`Grep`** for **each name separately** across the codebase

### 10.4 Example

```bash
# Step 1: Read the wrapper module to find all export aliases
Read: "pricing/index.js"
# Found: calculateDiscount is also exported as "getDiscount"

# Step 2: Search for the original name
Grep pattern: "calculateDiscount\("

# Step 3: Search for the wrapper/alias name too
Grep pattern: "getDiscount\("
```

### 10.5 Diagram: Full Tracing Flow

```
Find the function definition
        │
        ▼
Read the file(s) that export/wrap it
        │
        ▼
Identify ALL exported names/aliases
   (e.g. calculateDiscount, getDiscount)
        │
        ▼
Grep the codebase for EACH name separately
        │
        ▼
Combine all results = full picture of every usage
```

### 10.6 Why This Matters

Skipping this step can lead to an incomplete understanding of how widely a function is used — for example, if you're trying to safely rename or change a function's behavior, missing usages under a wrapper name could cause bugs elsewhere in the codebase that go unnoticed.

## 11. Full Worked Example: Combining the Tools

**Task:** "Find every place `sendNotification` is used, and fix a bug where it doesn't handle empty messages."

```bash
# Step 1: Glob to find likely relevant files first (optional narrowing)
Glob pattern: "**/*.js"

# Step 2: Grep to find where sendNotification is defined
Grep pattern: "function sendNotification"
# Found in: notifications/sender.js

# Step 3: Read the file to understand the function and check for wrapper exports
Read: "notifications/sender.js"
Read: "notifications/index.js"
# Found: sendNotification is also re-exported as "notify"

# Step 4: Grep for both names across the codebase
Grep pattern: "sendNotification\("
Grep pattern: "notify\("

# Step 5: Read each calling file to understand context before making changes
Read: "orders/checkout.js"
Read: "alerts/systemAlerts.js"

# Step 6: Try Edit to fix the bug in sender.js
Edit file: "notifications/sender.js"
Old text: "if (!message) { return; }"
# Fails — this exact line appears twice in the file

# Step 7: Fall back to Read + Write since Edit's match wasn't unique
Read: "notifications/sender.js"
# (identify the correct occurrence based on surrounding context)
Write: "notifications/sender.js"
Content: "...(full corrected file content)..."

# Step 8: Run tests to confirm the fix works
Bash: "npm test notifications"
```

This example uses every tool covered in this tutorial, in a realistic order.

## 12. Quick Reference: Common Mistakes and Fixes

| Mistake | Why It's a Problem | Fix |
|---------|---------------------|-----|
| Using `Grep` to find files by name | `Grep` searches content, not file names | Use `Glob` for name/path pattern matching instead |
| Using `Glob` to search inside file content | `Glob` doesn't look inside files at all | Use `Grep` for content search |
| Reading every file in the project upfront | Wastes time and context on irrelevant files | Start with `Grep`/`Glob` to find entry points, then `Read` only what's relevant |
| Forcing `Edit` on non-unique text | `Edit` will fail, since it can't tell which match you meant | Fall back to `Read` + `Write` for the full file |
| Searching only for a function's original name | Misses usages through wrapper/re-exported names | `Read` wrapper modules first, identify all export aliases, then `Grep` each one |
| Using `Read`/`Write` for a tiny one-line change | Slower and riskier than necessary; full rewrite invites mistakes | Prefer `Edit` when the anchor text is unique |

---

## 13. Summary

- `Grep` searches file **contents** (e.g. function calls, error messages, imports); `Glob` finds files by **name/path pattern** (e.g. `**/*.test.tsx`).
- `Read` loads a full file; `Write` creates or fully replaces a file; `Edit` makes a targeted change using **unique** text matching.
- If `Edit` fails because the target text is **not unique**, the reliable fallback is `Read` the full file, then `Write` the corrected full content back.
- `Bash` is for running actual commands — tests, installs, git operations — not just reading or editing files.
- Build codebase understanding **incrementally**: start with `Grep` to find entry points, then `Read` to follow imports and trace flows — don't read everything upfront.
- To fully trace a function's usage, first identify **all exported names/aliases** (including wrapper modules), then `Grep` for each name separately — searching only the original name can miss real usages.
