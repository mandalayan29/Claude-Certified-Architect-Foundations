# Domain 5: Context Management & Reliability
## Task Statement 5.1: Manage Conversation Context to Preserve Critical Information Across Long Interactions

---

## Why This Domain Matters

When you build agentic systems with Claude, conversations can become very long. A customer support agent may talk for 50 turns. A research agent may call 20 tools. As context grows, two things happen:

1. Claude may start to **forget or blur out important details** (like an exact refund amount or a date).
2. The context window fills up with **too much unnecessary data**, wasting tokens and pushing out useful information.

This section teaches you how to protect important facts, avoid data loss, and organize context so Claude gives reliable answers, even in long or complex conversations.

---

## Part 1: Understanding the Risks

### 1.1 Progressive Summarization Risk

**What is progressive summarization?**

When a conversation gets long, systems often summarize old messages to save space. This is called "progressive summarization" — you keep summarizing the summary as the conversation grows.

**The risk:**

Summarization is good at keeping the "general idea" of a conversation. But it is bad at keeping **exact facts**. Every time you summarize, small but important details can get lost or turned into vague language.

**Example of what gets lost:**

| Original Detail | After Summarization (Bad) |
|---|---|
| "Refund of $128.47 issued on March 3rd" | "A refund was issued" |
| "Customer expects delivery by June 15th" | "Customer has delivery expectations" |
| "Order #A29381, 3 units, 15% discount applied" | "Customer placed an order with a discount" |

Notice how **numbers, percentages, dates, and exact customer expectations** are the first things to disappear. This is dangerous because these are usually the most important facts in a business conversation — like refund amounts or deadlines.

**Rule to remember:** Never let numbers, dates, percentages, IDs, or customer promises pass through a summarization step. They must be preserved exactly, not "summarized."

---

### 1.2 The "Lost in the Middle" Effect

**What is it?**

Research on large language models (including Claude) shows that models pay more attention to information at the **beginning** and the **end** of a long input. Information placed in the **middle** of a long context is more likely to be missed or under-used.

**Why this happens (in simple terms):**

Think of reading a very long report. You usually remember the introduction and the conclusion clearly. The middle pages blur together, especially if the report is long and repetitive. Language models show a similar pattern.

**Why it matters for you:**

If you dump 10 tool results into the context, and the most important finding is tool result #5 (in the middle), Claude may not use it as effectively as tool result #1 or #10.

**What to do about it:**

- Do not just paste raw data in the order it arrived.
- Put the **most important summary or finding at the very beginning** of a large input.
- Repeat critical facts near the end too, if possible.
- Use clear section headers so Claude can "jump to" important parts, instead of relying purely on position.

---

### 1.3 Tool Results Accumulate and Waste Tokens

**The problem:**

When Claude calls a tool (like an order lookup API), the tool often returns a large JSON object with many fields — sometimes 40 or more. But for the actual task, you may only need 5 of those fields.

**Example:**

```json
{
  "order_id": "A29381",
  "customer_name": "John Smith",
  "customer_email": "john@example.com",
  "billing_address": "...",
  "shipping_address": "...",
  "payment_method": "...",
  "card_last4": "4242",
  "tax_amount": 4.32,
  "shipping_cost": 5.00,
  "item_sku_list": [...],
  "warehouse_location": "...",
  "carrier_tracking_id": "...",
  "loyalty_points_earned": 12,
  "internal_notes": "...",
  "order_status": "delivered",
  "order_total": 128.47,
  "return_window_days": 30,
  "...": "35 more fields"
}
```

If you keep passing this **entire object** into context every time you refer to the order, you are wasting a huge number of tokens on fields that are never used (like `card_last4` or `internal_notes`), while the actually useful fields (`order_status`, `order_total`, `return_window_days`) get buried inside a wall of text.

**Why this is a reliability problem, not just a cost problem:**

- Wasted tokens push older, useful conversation history out of the context window.
- A large irrelevant blob makes it harder for Claude to find the relevant fields (related to the "lost in the middle" effect).

**What to do about it:**

Trim tool outputs before they enter context. Keep only the fields relevant to the current task.

```python
# Full tool result comes back with 40+ fields
raw_order = get_order_details(order_id="A29381")

# Keep only fields relevant to a "return request" task
relevant_fields = ["order_id", "order_status", "order_total", "return_window_days"]
trimmed_order = {key: raw_order[key] for key in relevant_fields if key in raw_order}

# Only trimmed_order goes into the conversation context
```

This way, Claude sees a small, focused object instead of a massive one.

### 1.4 Passing Complete Conversation History

**The concept:**

The Claude API does not remember previous turns by itself. Every time you call the API, you must send the **full conversation history** (all previous user and assistant messages) as part of the `messages` array. If you leave out earlier turns, Claude will not know what was said before, and the conversation will lose coherence.

**Simple example:**

```python
messages = [
    {"role": "user", "content": "My order #A29381 hasn't arrived."},
    {"role": "assistant", "content": "I'm sorry to hear that. Let me check the status."},
    {"role": "user", "content": "It's been 2 weeks now."}
]

response = client.messages.create(
    model="claude-sonnet-4-6",
    max_tokens=1000,
    messages=messages
)
```

If, on the next turn, you only send the newest message and forget to include the earlier two, Claude will not know which order the user is talking about.

**Important exam point:** Claude (the model) is **stateless** between API calls. Memory across turns only exists because *you* resend the conversation history each time. This is why context management is your responsibility as the developer.

## Part 2: Skills — How to Actually Manage Context Well

### 2.1 Build a "Case Facts" Block

**What it is:**

A "case facts" block is a small, structured piece of text (or JSON) that holds the **critical transactional facts** of a conversation — separate from the general chat summary. This block is placed into **every prompt**, so key facts are never lost, even if the rest of the conversation gets summarized.

**What goes in it:**
- Amounts (money, quantities, percentages)
- Dates and deadlines
- Order numbers / IDs
- Status (e.g., "delivered," "refunded," "pending")

**Example structure:**

```json
{
  "case_facts": {
    "order_id": "A29381",
    "order_total": 128.47,
    "order_status": "delivered",
    "delivery_promised_date": "2026-06-15",
    "refund_amount": null,
    "customer_expectation": "Wants full refund due to late delivery"
  }
}
```

**How to use it:**

Every time you send a new prompt to Claude, you include this `case_facts` block near the top of the prompt — separate from the (possibly summarized) chat history.

```python
system_prompt = f"""
You are a customer support assistant.

CASE FACTS (always accurate, do not summarize or alter):
{case_facts_json}

Use the conversation history below for context, but always trust the CASE FACTS
block above for exact numbers, dates, and statuses.
"""
```

This way, even if the conversation history gets condensed or summarized, the exact facts remain safe and untouched.

---

### 2.2 Persist Structured Issue Data for Multi-Issue Sessions

**The scenario:**

Sometimes one conversation covers **multiple issues**. Example: a customer first asks about a late delivery (Order A), then later asks about a billing error (Order B).

**The risk:**

If you only keep one "case facts" block, the facts from Order A might get overwritten or mixed up when Order B comes in.

**The skill:**

Keep a **separate structured record for each issue**, instead of one single block. Think of it like a small database of issues within the conversation.

```json
{
  "issues": [
    {
      "issue_id": "issue_1",
      "order_id": "A29381",
      "amount": 128.47,
      "status": "delivered_late",
      "type": "delivery_delay"
    },
    {
      "issue_id": "issue_2",
      "order_id": "B77410",
      "amount": 45.00,
      "status": "overcharged",
      "type": "billing_error"
    }
  ]
}
```

Each issue keeps its own order ID, amount, and status. This way, Claude can correctly refer to "the first issue" or "the second issue" without mixing up facts.

### 2.3 Trim Verbose Tool Outputs Before They Accumulate

(This builds on section 1.3, but here is the **skill** in action.)

**Best practice steps:**

1. Decide, before calling the tool, which fields are actually relevant to the current task.
2. After the tool returns data, filter it down to only those fields.
3. Only add the trimmed version to context — never the raw full response.

**Example — Return Request Task:**

```python
def trim_for_return_request(order_data: dict) -> dict:
    """Keep only fields relevant to processing a return."""
    keep_fields = [
        "order_id",
        "order_status",
        "order_total",
        "return_window_days",
        "item_list"
    ]
    return {field: order_data.get(field) for field in keep_fields}

raw_order = get_order_details(order_id="A29381")
context_ready_order = trim_for_return_request(raw_order)
```

**Key exam point:** This should happen **before** the data is added to context, not after. The goal is to stop irrelevant data from ever entering the conversation history, not to clean it up later.

---

### 2.4 Placing Key Findings at the Beginning + Using Section Headers

**Why:** This directly fights the "lost in the middle" effect (see 1.2).

**Best practice pattern for aggregated inputs (example: combining results from multiple tool calls or subagents):**

```
## KEY FINDINGS SUMMARY (read this first)
- Refund approved: $128.47
- Reason: Delivery was 12 days late (promised June 15, delivered June 27)
- Action needed: Process refund within 3 business days

## DETAILED RESULTS

### Order Lookup Result
[full order details here]

### Delivery Tracking Result
[full tracking details here]

### Customer Communication History
[full message history here]
```

**Two techniques combined here:**
1. **Put the summary first** — so even if Claude only fully processes the start, it already has the key facts.
2. **Use explicit section headers** — so Claude (and a human reviewer) can quickly locate specific information, instead of relying only on position in the text.

---

### 2.5 Requiring Subagents to Include Metadata

**The scenario:**

In multi-agent systems, one agent (a "subagent") does research or lookups, and passes results to another agent (the "main" or "downstream" agent) for final synthesis.

**The risk:**

If a subagent just returns plain findings without saying **where the information came from** or **when it was gathered**, the downstream agent cannot judge how trustworthy or current the information is.

**The skill:**

Require every subagent output to include metadata, such as:
- **Date** the information was gathered or the date the fact refers to
- **Source location** (e.g., which document, database, or API endpoint)
- **Methodological context** (e.g., how the number was calculated or what method was used)

**Example structured subagent output:**

```json
{
  "finding": "Average customer refund processing time is 4.2 days",
  "date_collected": "2026-08-01",
  "source": "internal_refunds_database, table: refund_logs",
  "method": "Average calculated over refunds from the last 90 days"
}
```

Without this metadata, the downstream agent might treat an outdated or unreliable number as current fact.

---

### 2.6 Structured Data Instead of Verbose Content for Limited-Context Downstream Agents

**The scenario:**

Sometimes the downstream agent has a **small context budget** (it can only handle a limited amount of text). If the upstream agent sends long paragraphs of reasoning and explanation, the downstream agent may run out of space for the actually important facts.

**The skill:**

Change the upstream agent so that it returns **structured data** — key facts, citations, and relevance scores — instead of long explanations or reasoning chains.

**Bad example (verbose):**

```
"After carefully reviewing several sources, I found that the refund policy 
seems to generally allow returns within 30 days, although there was some 
nuance in section 4.2 of the policy document which discusses exceptions 
for international orders, and I also cross-referenced this with an older 
policy version to check for consistency..."
```

**Good example (structured):**

```json
{
  "key_facts": [
    "Standard return window: 30 days",
    "International orders: additional 15-day exception applies"
  ],
  "citations": ["policy_doc_v3, section 4.2"],
  "relevance_score": 0.95
}
```

The structured version gives the downstream agent exactly what it needs, in a compact form — no wasted tokens on reasoning that the downstream agent doesn't need to see.

## Part 3: Quick Summary Table (For Exam Review)

| Concept | Risk | Skill / Fix |
|---|---|---|
| Progressive summarization | Numbers, dates, percentages, promises get vague | Keep a separate "case facts" block, never summarize it |
| Lost in the middle | Middle-of-context info gets under-used | Put key findings first + use section headers |
| Tool result accumulation | 40+ fields consume tokens, bury relevant data | Trim tool outputs to only relevant fields before adding to context |
| Multi-issue sessions | Facts from different issues get mixed up | Persist structured, separate records per issue |
| Conversation history in API calls | Claude has no memory between calls | Always resend full conversation history each request |
| Subagent outputs | Downstream agent can't judge trust/freshness | Require metadata: dates, source, method |
| Limited context downstream agents | Verbose reasoning wastes limited space | Return structured facts, citations, relevance scores instead of prose |

## Key Takeaways

1. **Never let critical facts pass through summarization** — keep them in a protected, always-accurate block.
2. **Position matters** — put the most important information first, and use headers to organize the rest.
3. **Trim before you store** — don't let raw tool output bloat your context with irrelevant fields.
4. **Separate issues need separate structured records** — don't merge facts from different problems.
5. **You must resend full conversation history** — Claude does not remember previous API calls on its own.
6. **Subagent outputs need metadata** — dates, sources, and methods help downstream agents trust the data.
7. **Structured data beats prose** for downstream agents with limited context budgets.
