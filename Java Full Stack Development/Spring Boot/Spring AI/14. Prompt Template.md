# Configuring Spring AI to Use Ollama

## Goal

Now that Ollama is installed and working on our machine, let's connect it to our **Spring Boot application**, just like we did earlier with OpenAI.

## Step 1: Create a Separate Controller

Our existing controller (`OpenAIController`) is specifically built to work with **OpenAI**. Instead of modifying it directly, we create a **new controller** dedicated to Ollama, so both can exist separately in the project.

1. Create a new class: `OllamaController`
2. Copy the same overall structure/code from `OpenAIController` into this new class

### Important: Avoid Conflicts Between Controllers

Since both controllers use the **same URL mapping** (example: `/api/{message}`), running both at the same time will cause a conflict (Spring won't know which controller should handle the request).

To avoid this while testing, we temporarily **comment out or disable the mapping** in `OpenAIController`, so only `OllamaController` is active for now.

## Step 2: Add the Ollama Dependency

Right now, our project only has the **OpenAI** dependency in `pom.xml` — we need to add the **Ollama** dependency too.

### How to Find the Dependency

1. Go to `start.spring.io`
2. Click **Add Dependency**
3. Search for `Ollama`
4. Click **Explore** to see the exact dependency snippet

### Adding It to Your Project

Copy the Ollama dependency snippet and paste it into your existing `pom.xml` file (you do **not** need to create a brand-new project):

```xml
<dependency>
    <groupId>org.springframework.ai</groupId>
    <artifactId>spring-ai-ollama-spring-boot-starter</artifactId>
</dependency>
```

After adding this, your `pom.xml` now has **two** AI dependencies:

- `spring-ai-openai-spring-boot-starter`
- `spring-ai-ollama-spring-boot-starter`

> **Important:** After editing `pom.xml`, remember to **reload your Maven project** so the IDE picks up the new dependency.

## Step 3: Use `OllamaChatModel` in the Controller

Now, in `OllamaController`, instead of using `ChatModel` generically (which could match either provider), we specify `OllamaChatModel` directly:

```java
@RestController
public class OllamaController {

    private final ChatClient chatClient;

    public OllamaController(OllamaChatModel chatModel) {
        this.chatClient = ChatClient.create(chatModel);
    }

    // rest of the controller (same as before)
}
```

**Explanation:**

- `OllamaChatModel` → the specific chat model class for Ollama, made available because of the Ollama dependency we just added
- We create the `ChatClient` **programmatically**, using this specific model — the same programmatic approach we learned earlier when working with multiple providers

> **Tip:** If your IDE doesn't auto-suggest the correct import right away (sometimes happens due to loading delays), you can manually type the full import path, for example:
> `org.springframework.ai.ollama.OllamaChatModel`

## Step 4: Handling the "Two Models" Conflict

If you had earlier used `ChatClient.Builder` (auto-configured) in your project, adding a **second** AI dependency (Ollama, alongside OpenAI) can cause an error, because:

> Spring Boot cannot decide **automatically** which `ChatModel` to inject into the builder, since there are now **two** available (OpenAI's and Ollama's).

### How to Fix It

Since we now have multiple models, we should use the **programmatic approach** (`ChatClient.create(specificModel)`) instead of the auto-configured `ChatClient.Builder`. This means:

- In `OllamaController`, use `OllamaChatModel` specifically (as shown above)
- In `OpenAIController`, make sure it uses `OpenAiChatModel` specifically, rather than relying on the ambiguous auto-configured builder

This matches what we learned earlier: **use the Builder approach only when there is one model; use the programmatic approach when there are multiple models.**

## Step 5: Test It

1. Restart the application
2. Send a request: `tell me a joke`
3. You get a proper response back

This confirms that the connection to Ollama, through our Spring Boot code, is working.

## Understanding the Default Model Behavior

Here's something interesting: nowhere in our code have we explicitly told Ollama **which model** to use (like Mistral, DeepSeek, etc.) — yet it worked.

> By default, Spring AI's Ollama integration tries to use **Mistral** as the model, unless configured otherwise.

### What Happens If Mistral Isn't Available?

If Mistral is not downloaded on your local machine, the application will fail with an error, since it has nothing to fall back on automatically.

You can test this yourself by removing the Mistral model from your machine using Ollama's remove command:

**Syntax:**

```
ollama rm <model_name>
```

**Example:**

```
ollama rm mistral
```

**What it does:** Deletes the specified model from your local machine.

After removing Mistral and trying the same request again, the application throws an error — confirming that Spring AI was indeed relying on Mistral by default.

## Step 6: Explicitly Choosing a Different Model

If you don't want to use the default (Mistral), or if you simply want to use a different model (example: DeepSeek), you can configure it explicitly in `application.properties`.

**Syntax:**

```
spring.ai.ollama.chat.options.model=<model_name>
```

**Example:**

```
spring.ai.ollama.chat.options.model=deepseek-r1:7b
```

**Explanation:**

- `spring.ai.ollama.chat.options.model` → this property tells Spring AI's Ollama integration exactly which local model to use
- The value should match the exact model name/tag as shown in your `ollama list` output or Ollama's model page (example: `deepseek-r1:7b` for a 7-billion-parameter version of DeepSeek)

### Test Again

1. Restart the application
2. Send the same request again

**Result:** No error, and you get a proper response. If you check the logs/response details, it will now confirm that **DeepSeek** (or whichever model you configured) is being used, instead of the default Mistral.

## Key Takeaway: No API Key Needed

Unlike OpenAI, since Ollama runs the model **locally** on your own machine:

- You do **not** need any API key
- You do **not** need to add billing/credits
- Everything runs on your own system's resources

## Quick Summary

| Concept | Meaning |
|---|---|
| `OllamaChatModel` | The specific Spring AI class used to talk to models running via Ollama |
| `spring-ai-ollama-spring-boot-starter` | The Maven dependency needed to use Ollama with Spring AI |
| Default Ollama model in Spring AI | Mistral (used automatically unless configured otherwise) |
| `spring.ai.ollama.chat.options.model` | Property used to explicitly set which local model to use |
| `ollama rm <model_name>` | Command to delete/remove a downloaded model from your machine |
| Multiple models + `ChatClient.Builder` | Causes conflicts — use the programmatic approach instead when using multiple providers |

## Practice Questions

**Q1: Why was a separate `OllamaController` created instead of modifying the existing `OpenAIController`?**
A: To keep the code for each provider separate and organized, and to avoid mixing OpenAI-specific and Ollama-specific logic in the same controller.

**Q2: Which Maven dependency needs to be added to use Ollama with Spring AI?**
A: `spring-ai-ollama-spring-boot-starter`

**Q3: Why did using `ChatClient.Builder` cause an error after adding the Ollama dependency alongside OpenAI?**
A: Because Spring Boot could not automatically decide which `ChatModel` to inject, since there were now two available models (OpenAI's and Ollama's). The programmatic approach with a specific model type should be used instead.

**Q4: Which model does Spring AI use by default when connecting to Ollama, unless configured otherwise?**
A: Mistral.

**Q5: Which property is used to explicitly set which local Ollama model to use?**
A: `spring.ai.ollama.chat.options.model`

**Q6: Do you need an API key when using Ollama with Spring AI? Why or why not?**
A: No, because Ollama runs the model locally on your own machine, so there is no cloud service or billing involved.

**Q7: What command would you use to remove the "mistral" model from your local machine?**
A: `ollama rm mistral`
