# Adding Memory to Your Chat Using Advisors

## The Problem: LLMs Don't Remember Anything by Default

Let's test our application with a simple conversation flow.

1. Send a request: `tell me a joke`
2. We get a joke back — everything works fine

Now, just like we normally do on ChatGPT or similar tools, let's ask for more:

3. Send a request: `more`

**Result:** The AI gets confused and responds with something like:

> "It seems like your request is a bit vague. Could you please provide more context or specify what you..."

### Why Does This Happen?

This happens because **LLMs are memoryless by default**.

> Many people assume that AI models like OpenAI or Gemini automatically "remember" your earlier conversation. That is not actually true at the LLM level.

When you use tools like **ChatGPT**, it *feels* like it remembers your conversation — but that memory feature is built by the **tool itself** (like ChatGPT's interface), not something the raw LLM does automatically. The LLM itself only responds based on what is sent to it **in that single request** — it has no built-in memory of previous messages.

### Demonstration

To prove this point, imagine a simple ChatGPT-like UI connected to our own backend (not the real ChatGPT):

1. Ask: `tell me a joke` → get a joke
2. Ask: `more` → get the same vague, confused response as before

This confirms: **our own Spring AI backend does not remember previous messages**, just like the raw LLM behavior.

## The Goal: Make Our Application Remember the Conversation

We want our Spring AI application to **remember earlier messages**, so that when we say something like `more`, it understands the context from the previous question.

By default, Spring AI (and the underlying LLM) does **not** provide this automatically. We need to explicitly add this capability ourselves.

## Introducing Advisors

Spring AI provides a concept called **Advisors** to solve exactly this kind of problem — and more.

### What Is an Advisor?

Think of an **Advisor** as a checkpoint that sits **in between** your application and the LLM.

```
Your Application
      |
      v
  [ Advisor(s) ]   <-- can check/modify the outgoing request
      |
      v
     LLM
      |
      v
  [ Advisor(s) ]   <-- can check/modify the incoming response
      |
      v
Back to Your Application
```

Normally, if you don't add any advisor, your request goes straight to the LLM through Spring AI, and the response comes straight back — nothing extra happens in between.

With advisors, you can plug in extra logic at these points, such as:

- **Modifying** what you're sending before it reaches the LLM
- **Monitoring** what is being sent
- **Checking or modifying** the response coming back from the LLM
- **Safeguarding** your application (example: filtering or censoring certain content)
- **Providing memory** (remembering past conversation) — our focus in this topic

There are multiple types of advisors available for different purposes. In this topic, we will focus specifically on the one that provides **chat memory**.

## Adding a Memory Advisor

To add memory support, we update how we build our `ChatClient`, using the `ChatClient.Builder` we set up earlier.

### Step 1: Add `defaultAdvisors()`

Before calling `.build()`, we add a step to include our advisor:

```java
public OpenAIController(ChatClient.Builder builder) {
    this.chatClient = builder
            .defaultAdvisors(
                MessageChatMemoryAdvisor.builder(new InMemoryChatMemory()).build()
            )
            .build();
}
```

**Explanation:**

- `.defaultAdvisors(...)` → lets you attach one or more advisors to this `ChatClient`
- `MessageChatMemoryAdvisor` → the specific advisor responsible for **remembering the chat conversation**
- `InMemoryChatMemory` → tells the advisor **where** to store this memory — in this case, simply **in memory** (temporary storage inside the running application, not saved permanently)

> **Note:** Spring AI provides several advisor types (example: for memory, for safeguarding content, etc.). Here, we are only using the **memory advisor** to keep things simple.

### Understanding `InMemoryChatMemory`

`InMemoryChatMemory` is a class that **implements** the `ChatMemory` interface. It provides basic operations to manage conversation history, such as:

- Adding a new conversation/message
- Getting the stored conversation
- Clearing the memory

At this point, we don't need to manually manage all of this — we simply enable it, and the advisor handles the memory automatically behind the scenes.

> **About "before" and "after":** The chat memory advisor also supports hooking into the request **before** it is sent to the LLM, and the response **after** it comes back — this is how it manages to inject old conversation history into new requests. For now, we don't need to configure this manually; using the advisor with its default setup is enough.

## Full Example

```java
@RestController
public class OpenAIController {

    private final ChatClient chatClient;

    public OpenAIController(ChatClient.Builder builder) {
        this.chatClient = builder
                .defaultAdvisors(
                    MessageChatMemoryAdvisor.builder(new InMemoryChatMemory()).build()
                )
                .build();
    }

    @GetMapping("/api/{message}")
    public ResponseEntity<String> getAnswer(@PathVariable String message) {

        ChatResponse chatResponse = chatClient
                .prompt(message)
                .call()
                .chatResponse();

        String response = chatResponse
                .getResult()
                .getOutput()
                .getText();

        return ResponseEntity.ok(response);
    }
}
```

## Testing the Memory Feature

1. Restart the application
2. Send: `tell me a joke` → get a joke as expected
3. Send: `more`

**Result this time:** Instead of a confused/vague reply, the AI actually understands the context and gives **more jokes** related to the earlier conversation.

### Another Test

1. Send: `what is spring ai` → get a full explanation
2. Send: `explain in one line`

**Result:** The AI correctly understands that "explain in one line" refers to the previous topic (**Spring AI**) and gives a short, one-line explanation — because it now remembers the earlier message.

This confirms that our application is now successfully **remembering the conversation**, thanks to the memory advisor.

## Quick Summary

| Concept | Meaning |
|---|---|
| LLM memoryless behavior | By default, an LLM does not remember previous messages — each request is treated independently |
| Advisor | A checkpoint in Spring AI that sits between your app and the LLM, letting you monitor or modify requests/responses |
| `defaultAdvisors(...)` | Method used to attach one or more advisors to a `ChatClient` |
| `MessageChatMemoryAdvisor` | The specific advisor used to enable chat memory (remembering conversation) |
| `InMemoryChatMemory` | Stores the conversation history temporarily, in memory (not permanently saved) |

## Practice Questions

**Q1: Why did the application respond with a vague/confused message when we said "more" after asking for a joke?**
A: Because LLMs are memoryless by default — they don't remember previous messages unless the application explicitly provides that conversation history again.

**Q2: What is an Advisor in Spring AI?**
A: A checkpoint that sits between your application and the LLM, allowing you to monitor, modify, or enhance the outgoing request or the incoming response — used for things like memory, safeguarding content, and more.

**Q3: Which advisor is used to enable chat memory in this topic?**
A: `MessageChatMemoryAdvisor`

**Q4: What does `InMemoryChatMemory` do?**
A: It stores the conversation history temporarily, in memory, so that the advisor can reuse it in future requests. It is not permanent storage.

**Q5: How do you attach an advisor to a `ChatClient` built using `ChatClient.Builder`?**
A: By calling `.defaultAdvisors(...)` on the builder before calling `.build()`, and passing in the advisor object (example: `MessageChatMemoryAdvisor`).

**Q6: After adding the memory advisor, what changed when asking "more" after a previous question?**
A: Instead of a vague/confused response, the AI correctly understood the context from the earlier message and gave a relevant, related answer.
