# Implementing PgVector as Your VectorStore

## Step 1: Adding the Remaining Dependencies

Before writing any code, we need to make sure we have **all the required dependencies** in `pom.xml`. In the previous topic, we added the PgVector starter. Now, since we are also using **Docker Compose** to run PgVector, we need one more dependency:

```xml
<dependency>
    <groupId>org.springframework.boot</groupId>
    <artifactId>spring-boot-docker-compose</artifactId>
</dependency>
```

**Explanation:**

- This dependency helps Spring Boot **integrate with Docker Compose**, making it easier for your application to work alongside your Docker-managed services (like our PgVector container)

So in total, for PgVector support, we need:

1. `spring-ai-starter-vector-store-pgvector` → the PgVector-specific vector store starter
2. `spring-boot-docker-compose` → for Docker Compose integration

## Step 2: Updating the `VectorStore` Bean in `AppConfig`

Previously, our `AppConfig` class created a `SimpleVectorStore`:

```java
@Bean
public VectorStore vectorStore(EmbeddingModel embeddingModel) {
    return SimpleVectorStore.builder(embeddingModel).build();
}
```

Now, let's switch this to use **`PgVectorStore`** instead.

### An Important Difference: JDBC Is Needed

`SimpleVectorStore` used an **in-memory** store — meaning it didn't connect to any real, external database.

`PgVectorStore`, on the other hand, connects to a **real external database** (PostgreSQL). And whenever Java needs to talk to an external database, we know there's always something in between: **JDBC**.

So, along with the `EmbeddingModel`, we also need to provide a **`JdbcTemplate`** when building our `PgVectorStore`.

### Updated Code

```java
@Bean
public VectorStore vectorStore(EmbeddingModel embeddingModel, JdbcTemplate jdbcTemplate) {
    return PgVectorStore.builder(jdbcTemplate, embeddingModel).build();
}
```

**Explanation:**

- `JdbcTemplate jdbcTemplate` → Spring automatically provides this, since it's a standard Spring Data class used for talking to relational databases (Spring Boot auto-configures it once your database connection properties are set correctly)
- `PgVectorStore.builder(jdbcTemplate, embeddingModel).build()` → creates our `VectorStore`, but this time backed by PostgreSQL/PgVector, using both the JDBC connection and the embedding model

## Step 3: Running It (and Fixing Errors Along the Way)

Learning a new integration often involves some trial and error — let's walk through the actual issues encountered and how each one was resolved.

> **Before running:** Make sure your Docker container (from the previous topic) is up and running on port `5432`.

### Error 1: Bean Definition Conflict

**Error message (paraphrased):**

```
The bean 'vectorStore' defined in classpath... is being overridden
```

**What this means:** Since we're now using Docker Compose integration, Spring Boot may try to **auto-configure its own vector store bean** behind the scenes, which conflicts with our manually defined `vectorStore` bean.

**Fix:** Add this property to `application.properties`:

```
spring.main.allow-bean-definition-overriding=true
```

**Explanation:** This property tells Spring Boot that it's okay to **override** an existing bean definition with our own custom one, resolving the conflict.

### Error 2: "Bad Grammar" / Unknown Type "vector"

**Error message (paraphrased):**

```
Prepared statement has bad grammar; unknown type "vector"
```

**What this means:** The database doesn't recognize the special `vector` data type yet — usually because the required **database schema** (table structure) hasn't been properly initialized.

**Fix:** We need to load a **schema file** that sets up the correct table structure (including support for the `vector` type) when the application starts.

1. Get the schema SQL file (example: `init-schema.sql`) — provided in the course's GitHub repository
2. Place it inside your project's `resources` folder

Then, add these two properties to `application.properties`:

```
spring.sql.init.schema-locations=classpath:init-schema.sql
spring.sql.init.mode=always
```

**Explanation:**

- `spring.sql.init.schema-locations` → tells Spring Boot exactly which SQL file to run for initializing the schema
- `spring.sql.init.mode=always` → tells Spring Boot to **always** run this schema initialization on startup (rather than only under certain conditions)

### Error 3: Dimension Mismatch

**Error message (paraphrased):**

```
Bean definition failed... Expected dimension is 1536, but got 3072
```

**What this means:** There's a **mismatch** between the number of dimensions PgVector expects (based on configuration) and the number of dimensions actually being generated (based on which embedding model is being used).

In this case, the project was using OpenAI's `text-embedding-3-large` model, which produces **3072-dimension** embeddings — but PgVector was expecting **1536** (a different default).

### Fixing the Dimension Mismatch: Two Possible Approaches

#### Option A: Explicitly Set the Correct Dimensions

You can explicitly tell `PgVectorStore` how many dimensions to expect, matching your embedding model:

```java
@Bean
public VectorStore vectorStore(EmbeddingModel embeddingModel, JdbcTemplate jdbcTemplate) {
    return PgVectorStore.builder(jdbcTemplate, embeddingModel)
            .dimensions(3072)
            .build();
}
```

**Explanation:**

- `.dimensions(3072)` → explicitly sets the expected number of dimensions to `3072`, matching the `text-embedding-3-large` model's output

#### Option B: Switch to a Model That Matches the Default Dimensions

Alternatively, you can switch your embedding model configuration to one that naturally matches PgVector's default expected dimension (`1536`).

**Example: Using `text-embedding-ada-002` instead:**

```
spring.ai.openai.embedding.options.model=text-embedding-ada-002
```

**Explanation:**

- `text-embedding-ada-002` (an older OpenAI embedding model) produces exactly **1536** dimensions by default, matching PgVector's default expectation — no manual `.dimensions(...)` configuration needed in this case

> **Key takeaway:** Whichever embedding model you use, make sure the `dimensions` setting in `PgVectorStore` (if explicitly set) **matches** the actual number of dimensions your chosen embedding model produces. A mismatch between these two will cause errors.

## Step 4: Testing After the Fix

Once the dimension mismatch is resolved, restart the application — this time, it should start successfully.

### Testing the Search

```
POST http://localhost:8080/api/product?text=tea
```

**Result:** You get relevant results related to "tea," just like before with `SimpleVectorStore`.

```
POST http://localhost:8080/api/product?text=bag
```

**Result:** You get relevant results related to "bag."

> **Important observation:** The actual **search algorithm/logic hasn't changed at all** — we're still doing the same semantic similarity search as before. What **has** changed is **where the data is being stored** — now in a real, external PostgreSQL database (via PgVector), instead of in-memory.

## Additional Configuration Options for `PgVectorStore`

Beyond `dimensions`, `PgVectorStore`'s builder supports several other configuration options:

| Option | Purpose | Default (typically) |
|---|---|---|
| **Distance type** | How similarity/closeness between vectors is measured | Cosine distance |
| **Index type** | The indexing strategy used for efficient vector search | HNSW |
| **Schema name** | Which database schema to use | (configurable) |
| **Initialize schema** | Whether to automatically initialize the schema | Can be set to `true`/`false` |
| **Max document batch size** | Controls how many documents are processed together in one batch | (configurable) |

> These can all be configured using the builder pattern, similar to how we set `.dimensions(...)`, if you need more fine-grained control over how PgVector behaves.

## Important Things to Remember

- We used **Docker Compose** to run the PgVector container
- Several changes were needed in `application.properties`:
  - `spring.main.allow-bean-definition-overriding=true`
  - `spring.sql.init.schema-locations=classpath:init-schema.sql`
  - `spring.sql.init.mode=always`
  - Database connection properties (from the previous topic)
- The `AppConfig` class needed to be updated to build a `PgVectorStore` instead of a `SimpleVectorStore`, requiring both an `EmbeddingModel` and a `JdbcTemplate`
- **No changes were needed** in the controller or `DataInitializer` — they only depend on the `VectorStore` interface

> **Note:** Since this configuration is specific to PgVector, code shown in future topics may differ slightly, depending on whether `SimpleVectorStore`, PgVector, or another implementation is being used at that point.

## Practice Questions

**Q1: Why is a `JdbcTemplate` needed when building a `PgVectorStore`, but not when building a `SimpleVectorStore`?**
A: Because `SimpleVectorStore` is in-memory and doesn't connect to any external database, while `PgVectorStore` connects to a real PostgreSQL database — and JDBC is needed whenever Java communicates with an external database.

**Q2: What property resolves the "bean is being overridden" error encountered when adding Docker Compose integration?**
A: `spring.main.allow-bean-definition-overriding=true`

**Q3: Why did the application throw an "unknown type vector" error, and how was it fixed?**
A: Because the database's schema wasn't properly initialized with support for the `vector` data type. It was fixed by loading a schema SQL file using `spring.sql.init.schema-locations` and setting `spring.sql.init.mode=always`.

**Q4: What caused the "expected dimension is 1536 but got 3072" error, and what are the two ways to fix it?**
A: It was caused by a mismatch between PgVector's expected dimension size and the actual embedding model being used (`text-embedding-3-large`, which produces 3072 dimensions). It can be fixed either by explicitly setting `.dimensions(3072)` in the `PgVectorStore` builder, or by switching to an embedding model that matches the expected 1536 dimensions (example: `text-embedding-ada-002`).

**Q5: Did switching from `SimpleVectorStore` to `PgVectorStore` change the underlying search algorithm/logic?**
A: No — the same semantic similarity search logic is used either way. What changed is where the data (embeddings) is actually stored — now in an external PostgreSQL database instead of in-memory.
