# Working with ChatClient

## Why Move from ChatModel to ChatClient?

In the previous topic, we used `ChatModel` to talk to OpenAI. It worked, but it has **limited features**. It is good for very simple use cases, but it does not give us much control.

To get more control and a more fluent (easy-to-read, step-by-step) way of talking to the LLM, Spring AI provides another option: **ChatClient**.

With `ChatClient`, we can:

- Send a prompt and get a response (just like before)
- Get the response as a **single reply**, or as a **stream of messages**
- Get more control over the request and response (metadata, structured output, etc. — covered later)

### Important: ChatClient Uses ChatModel Internally

```
Your Code
   |
   v
ChatClient   <-- built on top of -->   ChatModel   <-->  LLM (OpenAI)
```

Even though we use `ChatClient` in our code, **behind the scenes, it still uses `ChatModel`** to actually talk to the LLM. So `ChatClient` is not a replacement for `ChatModel` — it is built **on top of** it.

## Another Benefit: Less Direct Binding to OpenAI

Notice something interesting: `ChatClient` comes directly from the **core Spring Framework** package, not from an OpenAI-specific package. This means our code does not explicitly say "I am using OpenAI" when we use `ChatClient` — making it a bit more flexible if you ever want to change providers.

## Step 1: Creating a ChatClient Object

Unlike `ChatModel`, Spring does **not automatically inject** a `ChatClient` object for you. You have to **create it yourself**, using a `ChatModel`.

So we still need `ChatModel` — we just use it differently.

### Code Example

```java
@RestController
public class OpenAIController {

    private final ChatClient chatClient;

    public OpenAIController(ChatModel chatModel) {
        this.chatClient = ChatClient.create(chatModel);
    }
}
```

**Explanation:**

- `ChatModel chatModel` → Spring still injects this for us automatically (same as before)
- `ChatClient.create(chatModel)` → a special method that builds a `ChatClient` object using the given `ChatModel`
- We store the result in a `ChatClient` field called `chatClient`, which we will use in our methods

> **Note:** `ChatClient` is an **interface**, introduced in Spring AI version `1.1.0`. Before this version, there was a different way of creating it.

> **Tip:** In more advanced setups, you can create the `ChatClient` in a separate configuration class (for example, to support multiple models). But for now, we are keeping it simple by creating it directly in the controller.

## Step 2: Using ChatClient to Send a Prompt

With `ChatModel`, we simply used `.call(message)`. With `ChatClient`, the flow is a bit different — but more powerful.

### The Three Main Steps

1. **`.prompt(...)`** → creates the prompt (the message you want to send)
2. **`.call()`** → actually sends the prompt to the LLM
3. **`.content()`** → extracts the plain text response

```
chatClient.prompt(message)  -->  builds the request (does NOT call LLM yet)
        |
        v
     .call()                -->  actually sends request to the LLM
        |
        v
     .content()              -->  extracts the plain text response (String)
```

### Understanding `.prompt()`

When you call `.prompt(...)`, there are **three ways** to use it:

| Option | Description |
|---|---|
| Blank prompt | Create an empty prompt, then add the message later |
| Prompt with a String | Directly pass your message as a simple `String` (what we use here) |
| Prompt with a `Prompt` object | Pass a fully built `Prompt` object (covered later in the course) |

For now, we use the simplest option — passing a `String` directly.

> **Important:** Calling `.prompt(message)` alone does **not** send anything to the LLM yet. It only builds a request object (`ChatClientRequestSpec`). The actual call to the LLM happens only when you call `.call()`.

### Understanding `.call()`

Once you call `.call()`, Spring AI actually sends the request to the LLM. But this method does not directly give you a `String` either — it returns another object called `CallResponseSpec`.

### Understanding `.content()`

To finally get the plain text answer as a `String`, you call `.content()` at the end.

### Full Code Example

```java
@RestController
public class OpenAIController {

    private final ChatClient chatClient;

    public OpenAIController(ChatModel chatModel) {
        this.chatClient = ChatClient.create(chatModel);
    }

    @GetMapping("/api/{message}")
    public String getAnswer(@PathVariable String message) {
        String response = chatClient
                .prompt(message)
                .call()
                .content();

        return "With ChatClient: " + response;
    }
}
```

**Explanation of the chained call:**

- `chatClient.prompt(message)` → builds the request using our message
- `.call()` → sends the request to OpenAI
- `.content()` → extracts just the plain text response from the result

This chained, step-by-step style (each part on its own line) makes the code **much easier to read**, compared to writing it all in one line like `chatClient.prompt(message).call().content()`.

1. Restart the server
2. Send the same type of request as before (example: asking for a joke)

**Example response:**

```
With ChatClient: Why did the computer go to therapy?
Because it had too many bytes from its past.
```

This confirms that `ChatClient` is working correctly.

## Why Use ChatClient Instead of Just ChatModel?

With plain `ChatModel`, you simply call `.call(message)` — very short and simple. With `ChatClient`, the code looks a bit longer, but you get **more control**, such as:

- Fetching just the `content()` (plain text), or
- Fetching the full `chatResponse()` (which includes extra details, like metadata)
- Later, generating **structured output** instead of plain text (covered in future topics)

So `ChatModel` is simple but limited, while `ChatClient` is slightly more code but far more flexible.

## Step 4: Returning a Proper HTTP Response (ResponseEntity)

So far, our method simply returns a `String`. This always sends back an HTTP status code of `200 (OK)` by default, no matter what actually happens internally.

To follow better practice, we can wrap our response using `ResponseEntity`, which allows us to control the **status code** properly (useful for handling errors in the future).

### Updated Code

```java
@RestController
public class OpenAIController {

    private final ChatClient chatClient;

    public OpenAIController(ChatModel chatModel) {
        this.chatClient = ChatClient.create(chatModel);
    }

    @GetMapping("/api/{message}")
    public ResponseEntity<String> getAnswer(@PathVariable String message) {
        String response = chatClient
                .prompt(message)
                .call()
                .content();

        return ResponseEntity.ok(response);
    }
}
```

**Explanation:**

- `ResponseEntity<String>` → the return type now represents a full HTTP response (status code + body), not just plain text
- `ResponseEntity.ok(response)` → returns an HTTP `200 OK` status, along with our response text as the body

> **Important:** Make sure you import `ResponseEntity` from the **Spring framework** package (`org.springframework.http.ResponseEntity`), not from any AI-related package.

### Test Again

Sending the same request still works correctly, and now the response is wrapped properly as an HTTP response with a status code.

## Quick Summary

| Concept | Meaning |
|---|---|
| `ChatClient` | A more flexible, fluent way to talk to an LLM, built on top of `ChatModel` |
| `ChatClient.create(chatModel)` | Creates a `ChatClient` object using an existing `ChatModel` |
| `.prompt(message)` | Builds the request (does not call the LLM yet) |
| `.call()` | Actually sends the request to the LLM |
| `.content()` | Extracts the plain text response as a `String` |
| `ResponseEntity<String>` | Wraps the response with proper HTTP status code control |
| `ResponseEntity.ok(response)` | Returns HTTP 200 status along with the response body |

## Practice Questions

**Q1: Does `ChatClient` replace `ChatModel`, or is it built on top of it?**
A: `ChatClient` is built on top of `ChatModel`. Behind the scenes, it still uses `ChatModel` to talk to the LLM.

**Q2: How do you create a `ChatClient` object in your code?**
A: By using `ChatClient.create(chatModel)`, passing in an existing `ChatModel` object (which Spring injects automatically).

**Q3: What are the three main chained method calls used to get a plain text response using `ChatClient`?**
A: `.prompt(message)`, followed by `.call()`, followed by `.content()`.

**Q4: Does calling `.prompt(message)` alone send the request to the LLM?**
A: No. It only builds the request object. The actual call to the LLM happens when `.call()` is invoked.

**Q5: What is one advantage of using `ChatClient` over plain `ChatModel`?**
A: It gives more control — such as fetching full chat responses (with metadata) instead of just plain content, and later supports structured output.

**Q6: Why was `ResponseEntity<String>` introduced instead of returning a plain `String`?**
A: To have proper control over the HTTP status code of the response, instead of always defaulting to `200 OK` regardless of what actually happened.
