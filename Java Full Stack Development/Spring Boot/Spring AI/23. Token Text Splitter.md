# Performing Semantic Search Using VectorStore

## Goal

Now that our product data is loaded into the vector store (from the previous topic), let's write the **controller code** to actually search this data using **semantic/similarity search**.

## Step 1: Inject `VectorStore` into the Controller

Just like we did in `DataInitializer`, we inject the shared `VectorStore` bean into our controller as well:

```java
@Autowired
private VectorStore vectorStore;
```

Since we already configured `VectorStore` as a reusable `@Bean` in our configuration class (from the previous topic), we can simply inject it here without creating it again.

## Step 2: The Simplest Way — `similaritySearch(text)`

`VectorStore` provides a method called **`similaritySearch`**, which does most of the work for us. There are actually **two versions** of this method — let's start with the simpler one.

**Syntax:**

```java
List<Document> results = vectorStore.similaritySearch(text);
```

**Explanation:**

- `.similaritySearch(text)` → takes your search text, converts it into an embedding behind the scenes, compares it against all stored documents, and returns the most relevant/similar ones
- The return type is a `List<Document>` (a list of Spring AI's `Document` objects), since multiple matching results can come back — not just one

### Basic Controller Method

```java
@PostMapping("/api/product")
public List<Document> getProducts(@RequestParam String text) {
    return vectorStore.similaritySearch(text);
}
```

This is surprisingly short — most of the complexity is handled internally by `VectorStore`.

## Step 3: Handling the "Two Embedding Models" Error Again

Just like before (when we generated embeddings directly), if your project has **both OpenAI and Ollama** configured, you may get an error about having **two embedding models** available — this time possibly in more than one place (example: both the controller and `DataInitializer`/configuration).

### Fixing It

Use `@Qualifier` wherever needed, to explicitly specify which embedding model bean to use:

```java
@Autowired
@Qualifier("openAiEmbeddingModel")
private EmbeddingModel embeddingModel;
```

> **Reminder:** This conflict only happens because multiple AI providers are configured in the same project. If your project uses just **one** provider, you won't run into this issue.

## Step 4: Running and Testing

Once the conflicts are resolved and the application starts successfully, you should see logs indicating that your document was **split into chunks** (example: *"splitting document into six chunks"*), followed by each chunk being processed and stored.

### Test 1: Searching for "variables"

```
POST http://localhost:8080/api/product?text=variables
```

**Result (example):** A few loosely related chunks come back — results may not always feel perfectly relevant, especially with a small practice dataset and default chunking settings.

### Test 2: Searching for "tea"

```
POST http://localhost:8080/api/product?text=tea
```

**Result (example):** Related items like "water bottles" and "kettle" show up — makes sense, since these are related to tea. However, some unrelated or unexpected results (example: "airpods") might also appear.

> **Why might unrelated results show up?** AI-based semantic search isn't always perfect — sometimes called "hallucination" in AI contexts. It can also happen because chunks are mixed together, or a word appears in an unrelated context somewhere within a chunk. This shows why **chunking configuration** (from the previous topic) really matters — vague or overly large chunks can blur meaning and reduce accuracy.

### Comparing Custom Chunking vs Default Chunking

When testing with **custom, more specific chunking settings** (like the ones we configured previously), results tended to be **more relevant and focused**, compared to using the **default** `TokenTextSplitter` settings.

> **Lesson:** Being specific and intentional with your chunking configuration generally produces better, more accurate semantic search results.

## Step 5: Limiting the Number of Results Using `SearchRequest`

By default, `similaritySearch(text)` may return **more results than you actually want**. To control this — for example, limiting results to just the **top 2 most relevant matches** — we use the second version of `similaritySearch`, along with a `SearchRequest` object.

### Building a `SearchRequest`

**Syntax:**

```java
SearchRequest searchRequest = SearchRequest.builder()
        .query(text)
        .topK(<number_of_results>)
        .build();
```

**Explanation:**

- `SearchRequest.builder()` → starts building a search configuration, using the Builder pattern
- `.query(text)` → sets the actual search text (the same `text` parameter we receive from the request)
- `.topK(<number>)` → limits the results to the **top N** most relevant matches
- `.build()` → finalizes and creates the `SearchRequest` object

**Example (limiting to top 2 results):**

```java
SearchRequest searchRequest = SearchRequest.builder()
        .query(text)
        .topK(2)
        .build();
```

### Using the Search Request

```java
List<Document> results = vectorStore.similaritySearch(searchRequest);
return results;
```

## Full Example Code

```java
@RestController
public class OpenAIController {

    @Autowired
    private VectorStore vectorStore;

    @PostMapping("/api/product")
    public List<Document> getProducts(@RequestParam String text) {

        SearchRequest searchRequest = SearchRequest.builder()
                .query(text)
                .topK(2)
                .build();

        return vectorStore.similaritySearch(searchRequest);
    }
}
```

## Step 6: Fine-Tuning Chunk Settings for Better Accuracy

Along with limiting results using `topK`, going back and **fine-tuning the chunking settings** (from the `TokenTextSplitter` configuration in the previous topic) also plays a big role in getting more accurate results.

For example, adjusting settings such as:

- Chunk size (in tokens) — example: increasing it to `5` (or a more suitable value for your data)
- Minimum chunk length — example: `100`

...can result in the document being split into **many more, smaller, more focused chunks** (example: `28` chunks instead of just `4` or `6`), which generally leads to **more precise search matches**.

> **Trade-off:** More chunks generally take **more time and resources** to process (since each chunk needs its own embedding), so there's a balance between accuracy and performance/cost, especially with larger real-world datasets.

### Final Test: Searching for "tea" (With Better Chunking + `topK(2)`)

```
POST http://localhost:8080/api/product?text=tea
```

**Result:** This time, only **2 highly relevant results** come back:

1. Organic Green Tea
2. Ceramic Coffee Cup / Mugs

This is a much cleaner, more accurate result — showing how **combining better chunking with `topK` limiting** significantly improves the quality of semantic search results.

## Quick Summary

| Concept | Meaning |
|---|---|
| `vectorStore.similaritySearch(text)` | Simplest way to perform a semantic search — returns relevant documents based on the search text |
| `SearchRequest` | A configurable way to perform similarity search, allowing control over things like result count |
| `SearchRequest.builder().query(text).topK(n).build()` | Builds a search request that returns only the top `n` most relevant results |
| Chunking configuration impact | More specific/fine-tuned chunking generally leads to more accurate, relevant search results |
| `topK` | Limits how many top matching results are returned from a similarity search |

## Practice Questions

**Q1: What does `vectorStore.similaritySearch(text)` do, in simple terms?**
A: It converts the given search text into an embedding, compares it against all stored document embeddings, and returns the most relevant/similar documents.

**Q2: Why might a semantic search sometimes return unrelated or unexpected results (example: "airpods" when searching for "tea")?**
A: This can happen due to imperfect AI matching (sometimes called hallucination), or because chunks contain mixed/blended content, making the embedding less precise — highlighting the importance of good chunking configuration.

**Q3: How do you limit the number of results returned by a similarity search to just the top 2 most relevant matches?**
A: By using a `SearchRequest`, built with `SearchRequest.builder().query(text).topK(2).build()`, and passing it to `vectorStore.similaritySearch(searchRequest)`.

**Q4: According to this topic, does using more specific/custom chunking settings generally produce better or worse search results compared to default settings?**
A: Better — more specific chunking settings generally lead to more accurate and relevant semantic search results.

**Q5: What is a potential trade-off of creating many more, smaller chunks from a document?**
A: While it can improve search accuracy, it generally requires more time and resources to process, since each chunk needs to be individually converted into an embedding.
