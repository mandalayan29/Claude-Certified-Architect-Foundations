# Implementing Speech-to-Text and Handling Large Audio Files

## Step 1: Accepting the Audio File

Let's now complete our `speechToText` method so it actually accepts the uploaded audio file.

```java
@PostMapping("/api/stt")
public String speechToText(@RequestParam MultipartFile file) {
    return "";
}
```

**Explanation:**

- `@RequestParam MultipartFile file` → accepts the uploaded audio file, matching the field name (`file`) we send from our API client

## Step 2: Calling the Transcription Model

Converting audio to text turns out to be very simple, using our injected `OpenAiAudioTranscriptionModel`:

```java
String transcript = audioModel.call(file.getResource());
return transcript;
```

**Explanation:**

- `audioModel.call(...)` → sends the audio to OpenAI's transcription model
- `file.getResource()` → converts our `MultipartFile` into a `Resource` object (just like we did earlier with image uploads), which is what `.call(...)` expects
- `.call(...)` directly returns a plain `String` — the transcribed text — so there's no need for extra steps like `.getResult().getOutput()...` this time; it's refreshingly simple!

## Full Example Code

```java
@RestController
public class AudioGenController {

    private OpenAiAudioTranscriptionModel audioModel;

    public AudioGenController(OpenAiAudioTranscriptionModel audioModel) {
        this.audioModel = audioModel;
    }

    @PostMapping("/api/stt")
    public String speechToText(@RequestParam MultipartFile file) {
        return audioModel.call(file.getResource());
    }
}
```

## Step 4: Testing with a Larger Audio File (Encountering an Error)

Now let's try with a much larger audio file — an actual recording of a longer video (several MB in size, compared to the earlier small clips which were only a few KB).

### The Error

```
413 Payload Too Large
```

**Error message (paraphrased):**

```
Maximum upload size exceeded
```

### Understanding the Cause

> This isn't actually an issue with Spring AI or our transcription code — it's a **default limit** built into Spring's web framework (specifically, Spring's **multipart file upload handling**). By default, Spring only allows file uploads up to **1 MB**.

Since our test file is significantly larger than 1 MB (some files being 8 MB, 14 MB, or more), this default limit blocks the upload before it even reaches our transcription logic.

## Step 5: Increasing the Maximum Upload Size

To fix this, we need to explicitly configure a larger file size limit in `application.properties`.

**Syntax:**

```
spring.servlet.multipart.max-file-size=<size>
```

**Example:**

```
spring.servlet.multipart.max-file-size=20MB
```

**Explanation:**

- This property controls the **maximum size** of an individual file that can be uploaded through a multipart request
- The value can be specified using units like `MB` (megabytes) or `KB` (kilobytes)

> **Practical tip:** When choosing this value, look at the actual size of the files you expect to handle, and set the limit comfortably above that. In this example, since some test files were around 14 MB, a limit of **20 MB** was chosen to provide some safe headroom.

## Step 6: Testing Again with the Larger File

After updating this property and restarting the application, uploading the larger audio file works correctly this time — no more "payload too large" error.

### A Timeout Consideration

> **Important:** Larger audio files naturally take longer to process. There's typically a default timeout involved (in this case, around **30 seconds**) — if transcription takes longer than that, you may encounter a **timeout error** instead. For most reasonably-sized files, this shouldn't be an issue, but it's worth being aware of for very long recordings.

### Result

Once processing completes successfully, the transcription correctly captures the spoken content from the longer video recording — including greetings, names, and the general topics discussed.

> **On accuracy again:** As with the shorter clips, transcription of longer content is generally quite accurate, though small imperfections (example: a misheard name) can still occur — this is expected behavior with current speech recognition technology, not a flaw in our implementation.

## Step 7: A Limitation Noticed — No Timestamps

While testing, an important limitation becomes clear: **the returned transcription is just plain text, with no timestamps included.**

### Why Timestamps Matter

If you want to use this transcription for something like **video subtitles**, timestamps are essential — they tell the video platform exactly **when** each piece of text should appear on screen, matching the audio.

```
Plain transcription (no timestamps):
"Welcome back... my name is..."

vs.

Timestamped transcription (needed for subtitles):
[00:00:01] "Welcome back..."
[00:00:03] "my name is..."
```

Without timestamps, this raw transcription output isn't directly usable as proper subtitle data.

## Quick Summary

| Concept | Meaning |
|---|---|
| `audioModel.call(file.getResource())` | Sends the audio file to OpenAI's transcription model and directly returns the transcribed text as a `String` |
| `spring.servlet.multipart.max-file-size` | Property used to increase Spring's default 1 MB file upload limit |
| Default multipart upload limit | 1 MB, unless explicitly increased via configuration |
| Timeout consideration | Larger files take longer to process; a default timeout (example: ~30 seconds) may apply |
| Missing timestamps | The basic transcription call returns plain text only — no timing information, which limits its usefulness for things like subtitles (addressed via options, covered next) |
