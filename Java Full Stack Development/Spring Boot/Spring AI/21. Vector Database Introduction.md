## The Problem: Normal Keyword Search Has Limits

Let's say we have a list of product details for an e-commerce website — including product title, description, price, category, and features.

If you search this data using a **normal keyword search** (example: a simple text match, like you'd do with SQL's `LIKE` or a basic "find" feature):

- Searching for **"Bluetooth"** → shows all products that literally contain the word "Bluetooth" ✅
- Searching for **"earbuds"** → shows all products that literally contain the word "earbuds" ✅
- Searching for **"headphones"** → shows **nothing**, even if the list actually contains something like *"Bluetooth AirPods"* ❌
- Searching for **"wearable"** → shows **nothing**, even though the list may contain items like smartwatches, which are clearly wearable devices ❌

### Why Does This Happen?

Normal keyword search only looks for an **exact word match**. If the exact word isn't present in the text, it simply won't find it — even if a very closely related product actually exists.

## Understanding the Bigger Picture: What Needs to Happen

To make semantic search work, here's the overall flow we need to build:

```
Step 1: User sends a search text (example: "wearable")
Step 2: Convert this search text into an embedding
Step 3: We ALSO need embeddings for every product in our data
Step 4: Compare the search embedding against every product's embedding (using similarity)
Step 5: Return the products with the highest similarity scores
```

### Step 2 Is Simple — Step 3 Is the Tricky Part

Converting the user's short search text into an embedding is easy — it's just one call to `embeddingModel.embed(text)`, exactly as we did before.

But converting **all the product data** into embeddings is more involved, because:

- The product data file is large — even in our practice example, it has around 30–40 products
- In a **real e-commerce application**, this could easily be **thousands or even millions of products**
- We can't just convert one giant block of text into a single embedding — we need a smarter approach

## The Standard Approach: Chunking + Embeddings + Vector Database

Here's the general process used in real-world applications for this kind of large-scale semantic search:

```
1. Start with a large document (example: all product data)
        |
        v
2. Break it down into smaller pieces ("chunks")
   (example: one chunk per product, or a small group of related info)
        |
        v
3. Convert each chunk into its own embedding
        |
        v
4. Store all these embeddings in a special database — a Vector Database
        |
        v
5. When a user searches, convert their search text into an embedding too,
   and compare it against the stored embeddings using similarity search
```

This is exactly why we introduced **Vector Databases** as a concept earlier — this is where they become genuinely useful.

## Introducing `VectorStore` in Spring AI

Spring AI provides a ready-made **interface** called `VectorStore`, which handles working with vector databases in a consistent way.

### What Can You Do With `VectorStore`?

The `VectorStore` interface provides several useful operations:

- **Add documents** — store one or multiple documents (as embeddings) into the vector store
- **Delete documents** — remove stored documents
- **Similarity search** — search for documents that are most similar/relevant to a given piece of text

> We will also explore "search requests" (a more advanced way to configure similarity searches) in later topics.

## `VectorStore` Is Just an Interface — You Need an Implementation

Since `VectorStore` is only an **interface**, Spring AI does not force you to use one specific database. Instead, it provides multiple **implementations**, so you can choose the one that fits your project.

### Some Available `VectorStore` Implementations

| Implementation | Notes |
|---|---|
| Azure | Cloud-based vector store |
| Cassandra | NoSQL database with vector support |
| Chroma | Popular, lightweight vector database |
| Elasticsearch | Well-known search engine with vector support |
| MariaDB | Relational database with vector support |
| Neo4j | Graph database with vector support |
| Oracle | Relational database with vector support |
| PgVector | PostgreSQL extension for vector storage |
| Redis | In-memory database with vector support |
| SAP | Enterprise database option |
| **SimpleVectorStore** | A basic, **in-built** implementation — good for learning/educational purposes |

> You are free to choose whichever database fits your project — but each option requires some setup (installing the database, adding its dependency, and configuring properties).

## Why We're Using `SimpleVectorStore` in This Course

For this course, we will use **`SimpleVectorStore`**, because:

- It is **built into Spring AI** — no extra installation needed
- It's ideal for **learning and understanding how VectorStore works**, before moving to a production-grade database

> **Important:** `SimpleVectorStore` is meant for **educational purposes only** — it is not recommended for real, production-level applications with large amounts of data.

## What Setup Would Look Like for a Real Database (Example: PgVector)

Just so you understand what's involved if you ever want to use a real production database, here's a general idea using **PgVector** (a PostgreSQL extension) as an example:

1. **Run PgVector** — either install it locally, or run it easily using **Docker Compose**
2. **Add the PgVector dependency** to your `pom.xml` file
3. **Add the required properties** in your `application.properties` file (connection details, etc.)

```
Install/Run Database (e.g., via Docker)
        |
        v
Add Dependency (pom.xml)
        |
        v
Configure Properties (application.properties)
        |
        v
Ready to use with VectorStore
```

> This is generally a **one-time setup** process. Similarly, other options like **Chroma** may not even require local installation — just adding the library/dependency and some configuration.

> **For this course**, we are intentionally skipping this real-database setup, and focusing on `SimpleVectorStore` instead, to keep things simple while learning the core concepts.

## Practice Questions

**Q1: Why does a normal keyword search fail to find "Bluetooth AirPods" when searching for "headphones"?**
A: Because normal keyword search only looks for exact word matches, and the word "headphones" doesn't literally appear in "Bluetooth AirPods" — even though they are conceptually related.

**Q2: What is "chunking," and why is it needed before creating embeddings for a large document?**
A: Chunking means breaking a large document into smaller pieces. It is needed because you cannot efficiently convert one huge block of text into a single meaningful embedding — smaller chunks allow more accurate and manageable embeddings.

**Q3: What is `VectorStore` in Spring AI?**
A: It is an interface provided by Spring AI for storing, deleting, and performing similarity searches on embeddings (documents), without needing to build this functionality from scratch.

**Q4: Why is `SimpleVectorStore` used in this course, instead of a production database like PgVector?**
A: Because `SimpleVectorStore` is built into Spring AI, requires no extra setup, and is well-suited for learning and understanding how `VectorStore` works — while production databases like PgVector require extra setup (installation, dependencies, configuration) and are better suited for real-world, large-scale applications.

**Q5: What are the general three steps needed to set up a real `VectorStore` implementation, like PgVector?**
A: (1) Install/run the database (e.g., via Docker Compose), (2) add its dependency to `pom.xml`, and (3) configure the required connection properties in `application.properties`.
