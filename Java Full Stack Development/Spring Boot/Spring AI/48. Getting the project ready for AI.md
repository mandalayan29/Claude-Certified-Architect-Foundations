# Setting Up Spring AI in an Existing Project

## Goal

Before we can build the actual AI features, we first need to **enable Spring AI** in this existing e-commerce backend project — since, unlike our earlier learning projects, this one wasn't set up with Spring AI from the start.

## Step 1: Adding Spring AI Version Properties in `pom.xml`

Open the project's `pom.xml` file. We need to add a **property** specifying which Spring AI version to use.

```xml
<properties>
    <spring-ai.version>1.0.0</spring-ai.version>
</properties>
```

**Explanation:**

- `spring-ai.version` → a property name used elsewhere in the file to reference the Spring AI version consistently
- `1.0.0` → the stable Spring AI version we're using (as introduced earlier in this course)

> **Common mistake to watch out for:** This property name uses a **hyphen** (`spring-ai.version`), not a dot (`spring.ai.version`) — a small typo here can cause dependency resolution errors. When in doubt, **copy-paste** from a reliable source instead of typing it manually.

## Step 2: Adding the OpenAI Starter Dependency

```xml
<dependency>
    <groupId>org.springframework.ai</groupId>
    <artifactId>spring-ai-starter-model-openai</artifactId>
</dependency>
```

**Explanation:**

- This is the same OpenAI starter dependency we've used throughout this course, giving our project access to Spring AI's OpenAI integration (`ChatClient`, `ChatModel`, `ImageModel`, etc.)

## Step 3: Adding Spring AI's Dependency Management (BOM)

```xml
<dependencyManagement>
    <dependencies>
        <dependency>
            <groupId>org.springframework.ai</groupId>
            <artifactId>spring-ai-bom</artifactId>
            <version>${spring-ai.version}</version>
            <type>pom</type>
            <scope>import</scope>
        </dependency>
    </dependencies>
</dependencyManagement>
```

**Explanation:**

- **BOM** stands for **Bill of Materials** — it's a special Maven mechanism that helps manage **consistent versions** across a group of related dependencies
- By importing the `spring-ai-bom`, we ensure all our Spring AI-related dependencies use compatible, matching versions, without needing to specify a version number on each individual dependency separately

> **Where do these snippets come from?** When creating a **brand-new** Spring Boot project through Spring Initializr (`start.spring.io`) and selecting an AI dependency (like OpenAI), all of this configuration — the version property, the starter dependency, and the BOM — is **automatically generated** for you. Since we're adding Spring AI to an **existing** project here, we need to add these pieces **manually** instead.

## Step 4: Reloading Maven

After making these changes to `pom.xml`, remember to **reload your Maven project** so your IDE downloads the new dependencies.

> If you encounter an error like *"not able to find artifact spring-ai-model..."*, double-check for typos — as mentioned earlier, a stray dot instead of a hyphen (or vice versa) in a property name is a common, easy-to-miss mistake.

You can verify the dependency was added successfully by checking your project's **External Libraries** (or equivalent, depending on your IDE) and confirming the OpenAI-related library is now listed.

## Step 5: Adding Required Properties in `application.properties`

Now that the dependencies are in place, we need to configure two essential properties — just like we did at the very start of this course.

### The API Key

```
spring.ai.openai.api-key=<YOUR_API_KEY>
```

**Explanation:**

- This is the same OpenAI API key configuration we've used since the beginning of this course

> **Security reminder:** As mentioned throughout this course, storing your API key directly in `application.properties` is convenient for learning/tutorials, but it is **not the safest approach** for real production applications. Consider using environment variables or a proper secrets management solution for real projects, and always avoid committing real API keys to public repositories.

### The Chat Model

```
spring.ai.openai.chat.options.model=gpt-4o
```

**Explanation:**

- Specifies which OpenAI chat model to use
- **Note:** Since AI models are updated frequently, it's worth checking OpenAI's current documentation for the latest recommended/available model name at the time you're following along, and updating this value accordingly

## Step 6: Testing the Basic Setup

At this point, restart the application just to confirm there are **no errors** — even though we haven't built any actual AI-powered endpoints yet. This confirms:

- The dependencies were added correctly
- The properties are configured correctly
- The application starts up cleanly, ready for the next step

## Step 7: Understanding What Happens When the "Generate" Button Is Clicked

Before writing backend code, let's trace through what's supposed to happen:

```
User clicks "Generate" (for description) on the frontend
        |
        v
Frontend sends a request to the backend (example: "generate a description using AI")
        |
        v
Backend's controller needs a matching endpoint/mapping to receive this request
        |
        v
To actually talk to the AI, the controller needs a ChatClient object
```

> We haven't built the actual controller mapping yet (that's coming in the next topic) — but we do need to make sure a `ChatClient` is available and ready to be used, once we get there.

## Step 8: Creating a Configuration Class for `ChatClient`

Just like in earlier topics of this course, we set up our `ChatClient` as a reusable Spring **Bean**, rather than creating it manually wherever it's needed.

### Organizing the Project

1. Create a new package/folder called **`config`**
2. Inside it, create a configuration class — example: `ChatClientConfig` (or more generally, something like `AppConfig`, if you plan to add other AI-related beans here too)

```java
@Configuration
public class ChatClientConfig {

    @Bean
    public ChatClient chatClient(ChatClient.Builder builder) {
        return builder.build();
    }
}
```

**Explanation:**

- `@Configuration` → marks this class as a source of bean definitions
- `ChatClient.Builder builder` → automatically injected by Spring (as we've seen many times throughout this course), since our project currently has only **one** AI model provider configured (OpenAI)
- `builder.build()` → creates our ready-to-use `ChatClient` object
- `@Bean` → makes this `ChatClient` object available for injection wherever it's needed elsewhere in the project (example: in our product controller, coming up next)

> **Why put this in a separate `config` class, instead of directly in the controller's constructor?** Either approach works technically (as we've seen in earlier topics of this course), but organizing shared setup like this into a dedicated configuration class helps keep things clean and organized, especially as a real project grows and potentially needs this `ChatClient` (or other AI-related beans) in multiple places.

## What We've Set Up So Far

```
1. pom.xml            --> Added Spring AI version property, OpenAI starter dependency, and BOM
2. application.properties --> Added API key and chat model configuration
3. config/ChatClientConfig --> Created a ChatClient bean, ready for injection
```

## Practice Questions

**Q1: What three things need to be added to `pom.xml` to enable Spring AI in an existing project?**
A: A `spring-ai.version` property, the OpenAI starter dependency (`spring-ai-starter-model-openai`), and the Spring AI BOM (`spring-ai-bom`) under dependency management.

**Q2: What is the purpose of the Spring AI BOM (Bill of Materials)?**
A: It ensures that all Spring AI-related dependencies use consistent, compatible versions, without needing to manually specify a version on each individual dependency.

**Q3: What two properties need to be added to `application.properties` to configure OpenAI for this project?**
A: `spring.ai.openai.api-key` (your API key) and `spring.ai.openai.chat.options.model` (which chat model to use).

**Q4: Why was a `ChatClient` bean created in a separate configuration class, instead of directly in the controller?**
A: To keep the project organized, especially since this shared `ChatClient` object might be needed in multiple places as the project grows — though creating it directly in a controller's constructor would also technically work.

**Q5: What happens when a user clicks the "Generate" button on the frontend, in terms of what the backend needs to handle it?**
A: The frontend sends a request to the backend; the backend's controller needs a matching endpoint (mapping) to receive this request, and it needs access to a `ChatClient` object to actually communicate with the AI model.
