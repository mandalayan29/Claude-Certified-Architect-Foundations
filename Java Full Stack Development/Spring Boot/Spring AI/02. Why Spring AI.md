# Why Do We Need Spring AI? (The Abstraction Problem)

## Can We Connect Directly to OpenAI or Anthropic?

In the previous topic, we learned that Spring AI acts as a middle layer between our application and LLM models. A natural question comes up:

> Can we skip Spring AI and connect our application directly to OpenAI or Anthropic?

The answer is: **Yes, we can.** Let's see how.

## Connecting Directly to OpenAI

OpenAI is one of the LLM providers, along with Anthropic, Azure OpenAI, and others. To use OpenAI in your application:

1. Create an OpenAI account (developer account)
2. Add credits to your account (OpenAI is a paid service, not free)
3. Get your **API key**
4. Use OpenAI's **SDK** in your code to send requests

### OpenAI SDKs

OpenAI provides SDKs (Software Development Kits) for multiple programming languages:

- JavaScript
- Python
- .NET
- **Java** (our focus here)

### Steps to Use OpenAI in a Java Project

1. Create a simple **Maven project**
2. Add the OpenAI Java dependency to your project
3. Import the OpenAI library/packages in your code
4. Add your API key as an **environment variable** (the SDK reads it automatically)
5. Write code to:
   - Set your prompt (example: `"Tell me a joke"`)
   - Set the model you want to use
   - Build and send the request
6. Receive the response back

This is quite simple. With just **one dependency** and a small piece of code, you can send a prompt to OpenAI and get a response — directly, without any extra layer in between.

## So Why Do We Need Spring AI At All?

If direct integration is this simple, it may seem like Spring AI is not needed. But the problem appears when we look at **other providers**.

### The Problem: Every Provider Works Differently

Let's look at **Anthropic** (Claude) as another example:

- Anthropic also provides an SDK, but at the time of this course, it is still in **beta**
- The code structure for Anthropic looks **different** from OpenAI's code
- Both will work, but each provider has its **own way** of writing the request

This creates a problem when your application needs to support **more than one model**.

```
Your Application
     |
     |--- OpenAI code (one style)
     |--- Anthropic code (different style)
     |--- Google code (different style)
     |--- Amazon code (different style)
```

If you write code that is tightly connected to **one specific provider**, then:

- If you ever want to **switch models** (example: move from OpenAI to Anthropic), you will need to **change a lot of code**
- If you want to **support multiple models** at the same time, you will need to write and maintain **separate code for each provider**

And remember — OpenAI and Anthropic are not the only two providers. There is a growing list of LLM providers, each with its own SDK and coding style.

## The Solution: Abstraction

To solve this problem, we need **abstraction** — a common, unified way to talk to any LLM model, without writing provider-specific code every time.

> **Abstraction** means hiding the different, complex details of each provider behind one simple, common interface.

One option is to build this abstraction layer **manually**:

- Create your own functions
- Inside each function, call the specific provider's code
- Your application calls your functions, not the provider directly

This works, but it takes a lot of **time and effort** to build and maintain.

### Spring AI Already Provides This Abstraction

Instead of building this abstraction ourselves, **Spring AI already provides it out of the box**. According to Spring AI's documentation, it supports major AI model providers, including:

| Provider |
|---|
| Anthropic |
| OpenAI |
| Microsoft (Azure OpenAI) |
| Amazon |
| Google |
| Ollama (for running models locally) |

In this course, we will mainly focus on three of these:

- **Anthropic**
- **OpenAI**
- **Ollama** (since we will also run a model on our local machine)

## Why Abstraction Matters for Companies

Most companies prefer using a framework like Spring AI because abstraction gives them:

- **Clean code** – no messy, provider-specific logic scattered around
- **Easy management** – simple to maintain and update
- **Flexibility** – easy to switch or add new LLM providers later without rewriting the whole application

## Quick Summary

| Approach | Pros | Cons |
|---|---|---|
| Direct SDK integration (OpenAI, Anthropic, etc.) | Simple for a single provider | Different code style per provider; hard to switch or support multiple models |
| Manual abstraction layer | Full control | Time-consuming to build and maintain |
| **Spring AI** | Built-in abstraction, clean code, supports many providers | Requires learning Spring AI's own API (covered in this course) |
