# Building the Generate Description Endpoint (Wiring, Before AI Logic)

## Step 1: Figuring Out What the Frontend Expects

Before writing backend code, it's important to check **what the frontend is actually sending**, so our backend endpoint matches correctly.

Looking at the frontend's "Add Product" component, we can determine:

- **Endpoint being called:** something like `generate description` (specifically, the API path used is `/product/generate-description`)
- **Parameters being sent:** `name` and `category`

> **Why these two specifically?** It makes sense — a good product description depends on knowing **what** the product is (its name) and **what kind of product** it is (its category). The frontend also ensures the user has entered both before allowing the "Generate" button to be used.

> **A general lesson here:** In a real team project, this kind of information (which endpoints exist, what parameters they expect) is usually documented somewhere (example: API documentation, a shared spec, or comments in the frontend code). In this case, since formal documentation wasn't available, we had to inspect the frontend code directly to figure out the expected contract — a common, practical skill when integrating with an existing frontend.

## Step 2: Creating the Controller Method (Structure First)

Let's add a new method to the existing `ProductController` — logically placed before the "add product" logic, though exact placement is a matter of preference/organization.

```java
@PostMapping("/product/generate-description")
public ResponseEntity<String> generateDescription(
        @RequestParam String name,
        @RequestParam String category) {

    try {
        // actual AI logic goes here

    } catch (Exception e) {
        return ResponseEntity.internalServerError().body(e.getMessage());
    }
}
```

**Explanation:**

- `@PostMapping("/product/generate-description")` → matches the exact URL the frontend is calling
- `@RequestParam String name` and `@RequestParam String category` → capture the two values sent by the frontend
- **Return type `ResponseEntity<String>`** → wraps our response with proper HTTP status handling (as we learned earlier in this course)
- **`try-catch` block** → since calling an external AI service could potentially fail (network issues, API errors, etc.), it's good practice to handle exceptions gracefully
- In the `catch` block, we return an appropriate **error response** (using `internalServerError()`, since something unexpected went wrong on our side), including the exception's message for debugging purposes

## Step 3: Delegating to the Service Layer

Following good practice (and the same pattern already used elsewhere in this project), we shouldn't put the actual AI logic directly inside the controller. Instead, we delegate this work to the **service layer**.

```java
String description = productService.generateDescription(name, category);

return ResponseEntity.ok(description);
```

**Explanation:**

- `productService.generateDescription(name, category)` → calls a method on our existing `ProductService`, passing along the `name` and `category` values
- This method doesn't exist yet — we'll need to create it in `ProductService`

> **Why delegate to the service layer?** This keeps our controller focused purely on handling HTTP requests/responses, while the actual business logic (including AI-related logic) lives in the service layer — matching the existing structure of this project (`ProductController` → `ProductService` → `ProductRepository`), and following good separation-of-concerns practice in general.

## Step 5: Testing the Wiring (Before Adding Real AI Logic)

This is an important, practical development habit: **verify each piece works before adding the next layer of complexity.**

1. Restart the application
2. On the frontend, fill in a product name (example: "My Phone") and category (example: "Mobile")
3. Click **"Generate"**

**Result:** The description field gets filled with: *"demo description"*

> This confirms that:
> - The frontend is correctly calling our new endpoint
> - Our controller mapping (`/product/generate-description`) is correct
> - The parameters (`name`, `category`) are being received correctly
> - The response flows all the way back to the frontend correctly

**Crucially: none of this involved AI yet** — we deliberately used a hardcoded placeholder value to confirm the entire "plumbing" (frontend → controller → service → back to frontend) works correctly, **before** introducing the added complexity of actually calling an AI model.

## Why This Step-by-Step Approach Matters

> This is a valuable debugging and development strategy: when building a feature with multiple moving parts (frontend, controller, service, and now AI integration), it's much easier to identify problems if you **verify each layer works correctly, one at a time**, rather than writing everything at once and then trying to figure out what went wrong if something fails.

```
Step 1: Confirm frontend --> controller mapping works (using a placeholder response)
Step 2: Confirm controller --> service delegation works (still using a placeholder)
Step 3: THEN add the actual AI logic inside the service method
```
