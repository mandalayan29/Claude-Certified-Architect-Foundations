# Setting Up PgVector with Docker Compose

## What We Need Before Starting

To use PgVector, we first need **Docker** installed and running on our machine, since we will run PgVector as a **Docker container**.

> This tutorial assumes Docker is already installed. Setting up Docker itself is outside the scope of this course — if you don't have it yet, install Docker Desktop (or the appropriate Docker setup for your OS) first.

## Step 1: Understanding Docker Compose

**Docker Compose** lets you define your container setup (image, environment variables, ports, etc.) in a single file, and then start everything with one simple command.

**Syntax:**

```
docker compose up -d
```

**Explanation:**

- `docker compose up` → starts the containers defined in your Docker Compose file
- `-d` → runs the containers in **detached mode** (in the background, so your terminal isn't blocked)

> **Important:** This command only works if a Docker Compose file (commonly named `docker-compose.yml`) exists in the folder where you run the command. Without it, you'll get an error like:
> `no configuration file provided`

## Step 2: Creating the Docker Compose File

We place a `docker-compose.yml` file at the **root level** of our project. This tutorial does not go into full Docker syntax details (since this isn't a Docker-focused course), but here's what the file generally needs to specify:

```yaml
services:
  pgvector:
    image: pgvector/pgvector:pg16
    environment:
      POSTGRES_DB: telescope
      POSTGRES_USER: postgres
      POSTGRES_PASSWORD: "1234"
    ports:
      - "5432:5432"
```

**Explanation of key parts:**

- **Image** → tells Docker to use the official **PgVector** image (which already includes PostgreSQL)
- **Environment variables** → used to configure the database when the container starts:
  - **Database name** (example: `telescope`)
  - **Username** (example: `postgres`)
  - **Password** (example: `1234`)
- **Port** → PostgreSQL (and PgVector) typically runs on port `5432`

> **Note:** You can find the exact Docker Compose file used in this course in the accompanying GitHub repository — you don't need to type it all out manually.

## Step 3: Running the Docker Compose File

Once your `docker-compose.yml` file is in place, run:

```
docker compose up -d
```

**What happens:**

1. If the PgVector image isn't already downloaded on your machine, Docker will **download it first** (this may take some time depending on your internet speed)
2. Once downloaded, Docker will **create and start** the container based on your configuration

### Verifying It's Running

You can verify this worked in a couple of ways:

- Check your terminal output — it should confirm the container was created and started
- Open **Docker Desktop** (or run `docker ps`) and look at your running containers — you should see your PgVector container listed and running

> **Important detail to remember:** The container runs on **port `5432`** — you'll need this when configuring your Spring Boot application to connect to it.

## Step 4: Adding the PgVector Dependency

Now that PgVector is running, let's connect our Spring Boot project to it. First, we need to add the correct dependency to `pom.xml`.

We already have the general **Vector Store** support (from using `SimpleVectorStore` earlier). Now, we need to add the **PgVector-specific** starter dependency as well.

```xml
<dependency>
    <groupId>org.springframework.ai</groupId>
    <artifactId>spring-ai-starter-vector-store-pgvector</artifactId>
</dependency>
```

**Explanation:**

- This is the **starter dependency** specific to PgVector, separate from the general Spring AI/vector store dependencies we already had
- After adding this, remember to **reload your Maven project**, so your IDE picks up the new dependency

> **Reminder:** As covered in an earlier topic, Spring AI has moved to a stable release, so dependency names may look slightly different depending on the version you're using — always double check against the latest Spring Initializr output or official documentation if something doesn't match exactly.

## Step 5: Configuring Database Connection Properties

Since we're now connecting to a real PostgreSQL-based database, we need to add standard **database connection properties** to `application.properties` — just like you would for any typical Spring project that uses a database.

### Required Properties

**Syntax:**

```
spring.datasource.url=jdbc:postgresql://<host>:<port>/<database_name>
spring.datasource.username=<username>
spring.datasource.password=<password>
```

**Example (matching our Docker Compose setup):**

```
spring.datasource.url=jdbc:postgresql://localhost:5432/telescope
spring.datasource.username=postgres
spring.datasource.password=1234
```

**Explanation:**

- `spring.datasource.url` → the full connection string to your PostgreSQL database:
  - `jdbc:postgresql://` → indicates we're connecting to a PostgreSQL database using JDBC
  - `localhost:5432` → the host and port where our Docker container is running
  - `telescope` → the database name (matches what we set in the Docker Compose file)
- `spring.datasource.username` → matches the username set in Docker Compose (`postgres`)
- `spring.datasource.password` → matches the password set in Docker Compose (`1234`)

### A Couple of Additional Properties

Along with the basic connection details, a couple of extra standard Spring Data properties are typically needed as well:

```
spring.jpa.hibernate.ddl-auto=<value>
spring.datasource.driver-class-name=org.postgresql.Driver
```

> **Note:** These are common, standard Spring Boot database configuration properties — not something unique to PgVector or Spring AI specifically. If you've worked with Spring and databases before, these should look familiar.

## Step 6: Checking Our Progress So Far

At this point, here's what we've configured:

```
1. Docker Compose file --> runs PgVector (PostgreSQL + vector support) in a container
2. pom.xml --> added the PgVector-specific starter dependency
3. application.properties --> added database connection properties (URL, username, password, driver, etc.)
```

> **Important:** It's not guaranteed everything will work perfectly on the first try — and that's completely normal! If something doesn't work as expected, we may need to add a bit more configuration. This trial-and-error process is a normal part of learning how a new integration works.

## What's Left to Change in Our Code

Here's an important and reassuring point: **we don't need to change anything in our controller code.**

Why? Because:

- Our **controller** only depends on the `VectorStore` **interface** — it has no idea which specific implementation (SimpleVectorStore, PgVector, etc.) is actually being used behind the scenes
- Our **`DataInitializer`** class also simply auto-wires (`@Autowired`) the `VectorStore` — again, with no knowledge of the specific implementation
- The **only place** where we actually specify *which* `VectorStore` implementation to use is inside our **`AppConfig`** class (the configuration class we created earlier)

```
Controller             --> uses VectorStore interface (implementation-agnostic)
DataInitializer         --> uses VectorStore interface (implementation-agnostic)
AppConfig (@Bean)       --> THIS is where we specify the actual implementation
```

This is a great demonstration of why using **interfaces and abstraction** (like `VectorStore`) is so useful — switching from `SimpleVectorStore` to `PgVector` mainly involves changes in **configuration**, not in our core business logic.

## Quick Summary

| Concept | Meaning |
|---|---|
| `docker compose up -d` | Command to start containers defined in a Docker Compose file, running in the background |
| Docker Compose file | Defines the PgVector image, environment variables (DB name, user, password), and port |
| PgVector starter dependency | `spring-ai-starter-vector-store-pgvector`, added on top of the general vector store dependency |
| `spring.datasource.url/username/password` | Standard Spring Boot properties used to connect to the PostgreSQL/PgVector database |
| Why controller code doesn't change | Both the controller and `DataInitializer` depend only on the `VectorStore` interface — the actual implementation is specified only in `AppConfig` |

A: An error like "no configuration file provided."

A: Because both classes only depend on the `VectorStore` interface, not any specific implementation. The actual implementation being used is only specified in the `AppConfig` configuration class.
