# Loading Data into a Vector Store

## Goal

Now let's actually implement the first part of semantic search: **loading our product data into a vector database**, so that it can later be searched using similarity.

## The Overall Plan

```
1. Read the product data file
2. Break it down into smaller chunks
3. Convert each chunk into a document (Spring AI will handle the embedding behind the scenes)
4. Store these documents in a Vector Store
```

We'll build this step by step.

## Step 1: Create a Data Initializer Class

Instead of writing this loading logic directly inside our controller, we create a **separate class** dedicated to initializing our data.

```java
@Component
public class DataInitializer {

    public void init() {
        // logic goes here
    }
}
```

**Explanation:**

- `@Component` → tells Spring to manage this class as a bean, so it can participate in dependency injection
- We'll fill in the `init()` method step by step

## Step 2: Reading the File Using `TextReader`

Spring AI provides a class called **`TextReader`**, which helps us read text content from a file.

**Syntax:**

```java
TextReader textReader = new TextReader(new ClassPathResource("<file_name>"));
```

**Example:**

```java
TextReader textReader = new TextReader(new ClassPathResource("product_details.txt"));
```

**Explanation:**

- `ClassPathResource("product_details.txt")` → tells Spring where to find the file (in this case, inside the `resources` folder)
- `TextReader` → wraps this file so Spring AI can read its contents in a structured way

## Step 3: Setting Up the VectorStore as a Reusable Bean

Since we'll need our `VectorStore` object in **multiple places** (both in `DataInitializer` and in our controller), it makes sense to create it **once**, as a reusable Spring **Bean**, instead of creating it separately every time.

### Creating a Configuration Class

```java
@Configuration
public class AppConfig {

    @Bean
    public VectorStore vectorStore(EmbeddingModel embeddingModel) {
        return SimpleVectorStore.builder(embeddingModel).build();
    }
}
```

**Explanation:**

- `@Configuration` → marks this class as a source of bean definitions
- `@Bean` → tells Spring that this method produces an object (`VectorStore`) that should be managed and made available for injection elsewhere
- `SimpleVectorStore.builder(embeddingModel).build()` → creates a `SimpleVectorStore` object, using the **Builder pattern**. It requires an `EmbeddingModel`, which Spring automatically provides (injects) as a method parameter
- `SimpleVectorStore` → the specific, built-in implementation of `VectorStore` we chose earlier (good for learning purposes)

> **Note:** If you ever switch to a different `VectorStore` implementation (example: PgVector, Chroma, etc.), you would only need to change the code **inside this configuration class** — the rest of your application (like the controller and data initializer) can stay the same, since they only depend on the `VectorStore` interface, not a specific implementation.

## Step 4: Injecting VectorStore into DataInitializer

Now that `VectorStore` is available as a bean, we can inject it wherever we need it — including inside `DataInitializer`.

```java
@Component
public class DataInitializer {

    @Autowired
    private VectorStore vectorStore;

    public void init() {
        // logic goes here
    }
}
```

## Step 5: Breaking the File into Chunks Using `TokenTextSplitter`

We now have the raw file content (via `TextReader`), but we still need to break it down into smaller **chunks**, so each chunk can become its own document (and eventually, its own embedding).

Spring AI provides a class for exactly this purpose: **`TokenTextSplitter`**.

### Using Default Settings

```java
TokenTextSplitter splitter = new TokenTextSplitter();
```

This uses **default values** for chunking behavior (explained in detail below).

### Splitting the Document

```java
List<Document> documents = splitter.split(textReader.get());
```

**Explanation:**

- `textReader.get()` → retrieves the file's content as a document (or list of documents)
- `splitter.split(...)` → breaks this content down into **multiple smaller documents (chunks)**, based on the splitter's configuration
- The result, `documents`, is a `List` of `Document` objects — each representing one chunk of our original file

> **Important:** Make sure you use the correct `Document` class — the one provided by **Spring AI**, not any other unrelated `Document` class that might exist in your project's dependencies.

## Step 6: Adding the Documents to the Vector Store

Once we have our list of chunked documents, we simply add them to our `VectorStore`:

```java
vectorStore.add(documents);
```

**Explanation:**

- `.add(documents)` → stores all the given documents into the vector store
- Behind the scenes, Spring AI automatically converts each document into its **embedding**, and stores it appropriately — we don't need to manually call `embeddingModel.embed(...)` ourselves here

## Step 7: Running This Automatically on Application Startup

We want this data-loading process to happen **once**, automatically, when the application starts — not manually triggered every time.

We achieve this using the `@PostConstruct` annotation.

```java
@PostConstruct
public void init() {
    // logic here runs automatically after the bean is created
}
```

**Explanation:**

- `@PostConstruct` → tells Spring to automatically call this method **once**, right after the bean (`DataInitializer`) is fully created and ready — which effectively means it runs when the application starts

## Full Example Code

```java
@Component
public class DataInitializer {

    @Autowired
    private VectorStore vectorStore;

    @PostConstruct
    public void init() {
        TextReader textReader = new TextReader(new ClassPathResource("product_details.txt"));

        TokenTextSplitter splitter = new TokenTextSplitter();

        List<Document> documents = splitter.split(textReader.get());

        vectorStore.add(documents);
    }
}
```

```java
@Configuration
public class AppConfig {

    @Bean
    public VectorStore vectorStore(EmbeddingModel embeddingModel) {
        return SimpleVectorStore.builder(embeddingModel).build();
    }
}
```

## Understanding `TokenTextSplitter`'s Configuration Options

Instead of using the default settings, `TokenTextSplitter` also provides a **parameterized constructor**, letting you fine-tune exactly how chunking should work.

### Configuration Parameters

| Parameter | Meaning |
|---|---|
| **Chunk size** | The size of each chunk, measured in **tokens** |
| **Minimum chunk size (characters)** | The minimum number of characters a chunk should have; smaller chunks may be discarded |
| **Minimum chunk length to embed** | If a chunk has fewer tokens than this value, it gets discarded |
| **Maximum number of chunks** | A hard limit on how many chunks can be created in total |
| **Keep separator** | Whether to preserve line breaks/separators in the chunk text (`true`/`false`) |

### Choosing Chunk Size

> Ideally, chunk size should depend on the **context size** of the AI model you're using. For example, a large model might support up to 8000 tokens — but you should leave some room for your actual query text too, so you might set your chunk size a bit lower (example: `500`), rather than using the model's full capacity.

### Controlling Maximum Chunks

> If you're working with a very large document (example: an entire book or movie script), you may want to **limit** the total number of chunks created, to avoid generating too many. If you don't want any limit, you can use the maximum possible integer value instead.

### Example: Custom Configuration

```java
TokenTextSplitter splitter = new TokenTextSplitter(
    500,    // chunk size (in tokens)
    30,     // minimum chunk size in characters
    20,     // minimum chunk length to embed (in tokens)
    20,     // maximum number of chunks
    false   // keep separator
);
```

**Explanation of this example:**

- `500` → each chunk should be around 500 tokens
- `30` → a chunk should have at least 30 characters to be considered valid
- `20` → a chunk with fewer than 20 tokens gets discarded
- `20` → limit the total number of chunks to 20 (reasonable for a small practice dataset like ours)
- `false` → don't preserve line-break separators in the chunk text

> Both the **default constructor** and this **custom, parameterized constructor** are valid options — you can choose whichever fits your use case. For small documents (like our practice data), defaults may work fine; for larger, more complex documents, fine-tuning these values becomes more important.

## Quick Summary

| Concept | Meaning |
|---|---|
| `TextReader` | Spring AI class used to read text content from a file |
| `ClassPathResource` | Used to reference a file located in the project's `resources` folder |
| `TokenTextSplitter` | Spring AI class used to break a document into smaller chunks |
| `VectorStore.add(documents)` | Adds a list of documents (chunks) to the vector store, automatically generating embeddings behind the scenes |
| `@PostConstruct` | Ensures a method runs automatically once, right after the bean is created (e.g., at application startup) |
| `@Bean` (in a `@Configuration` class) | Creates a reusable, shared object (like `VectorStore`) that can be injected wherever needed |

## Practice Questions

**Q1: What is the purpose of the `TextReader` class in this context?**
A: It reads text content from a specified file (using `ClassPathResource`), so it can later be processed and split into chunks.

**Q2: Why do we break a large document into smaller chunks before storing it in a vector store?**
A: Because converting one huge block of text into a single embedding isn't practical or accurate; smaller chunks allow more precise, manageable embeddings, each representing a smaller, focused piece of content.

**Q3: What does `vectorStore.add(documents)` do, and does it manually require calling `embeddingModel.embed()` first?**
A: It stores the list of documents into the vector store. No manual embedding call is needed — the vector store automatically converts each document into its embedding behind the scenes.

**Q4: What is the purpose of the `@PostConstruct` annotation in the `DataInitializer` class?**
A: It ensures that the data-loading method runs automatically, once, right after the bean is created — effectively initializing the data as soon as the application starts.

**Q5: Why was `VectorStore` created as a `@Bean` inside a separate configuration class, rather than being created directly inside `DataInitializer`?**
A: So that the same `VectorStore` object can be reused across multiple classes (like the controller and the data initializer), instead of creating it repeatedly, and so switching to a different vector store implementation later only requires changing the configuration class.

**Q6: Name any two configuration parameters available in `TokenTextSplitter`'s custom constructor.**
A: Any two of: chunk size (in tokens), minimum chunk size (in characters), minimum chunk length to embed (in tokens), maximum number of chunks, and keep separator (true/false).
