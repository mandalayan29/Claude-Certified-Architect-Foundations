# Generating Your First AI Image

## Step 1: Create the Controller Method

Let's write the method that accepts a text description and generates an image based on it.

```java
@GetMapping("/image/{query}")
public String genImage(@PathVariable String query) {
    return "";
}
```

**Explanation:**

- `@GetMapping("/image/{query}")` → maps this method to handle `GET` requests, with the description passed directly in the URL path
- `@PathVariable String query` → captures the text description from the URL
- **Return type `String`** → for now, we'll return the result as a `String` (the image link) — we'll discuss returning an actual image separately, if needed

## Step 2: Creating an `ImagePrompt`

Just like we used `PromptTemplate`/`Prompt` for text-based chat earlier, image generation uses its own equivalent: **`ImagePrompt`**.

**Syntax:**

```java
ImagePrompt prompt = new ImagePrompt(query);
```

**Explanation:**

- `new ImagePrompt(query)` → creates an `ImagePrompt` object, using one of its constructors that simply accepts your text description as a `String`
- `ImagePrompt` supports other constructors too (for adding extra configuration, like image size/quality — covered in the next topic), but for now, we're using the simplest version

## Step 3: Calling the Image Model

Once we have our `ImagePrompt` ready, we send it to the model using `.call(...)`:

```java
ImageResponse response = openAiImageModel.call(prompt);
```

**Explanation:**

- `openAiImageModel.call(prompt)` → sends our `ImagePrompt` to OpenAI's image model and returns an `ImageResponse` object
- This is very similar in structure to how `ChatModel.call(...)` worked for text earlier in the course

## Step 4: Extracting the Image Link from the Response

The `ImageResponse` object contains the actual generated result, but we need to dig a little to get the usable image link (URL).

**Syntax:**

```java
String imageUrl = response.getResult().getOutput().toString();
```

Or, depending on the exact method available:

```java
String imageUrl = String.valueOf(response.getResult().getOutput());
```

**Explanation:**

- `response.getResult()` → gets the main result from the response
- `.getOutput()` → gets the actual output details — in this case, the generated image's information, including its **URL**
- As discussed in the previous topic, OpenAI's image generation typically returns a **link (URL)** to the generated image, rather than raw image data

## Full Example Code

```java
@RestController
public class ImageGenController {

    private OpenAiImageModel openAiImageModel;
    private ChatClient chatClient;

    public ImageGenController(OpenAiImageModel openAiImageModel, ChatModel chatModel) {
        this.openAiImageModel = openAiImageModel;
        this.chatClient = ChatClient.create(chatModel);
    }

    @GetMapping("/image/{query}")
    public String genImage(@PathVariable String query) {

        ImagePrompt prompt = new ImagePrompt(query);

        ImageResponse response = openAiImageModel.call(prompt);

        return response.getResult().getOutput().toString();
    }
}
```

> **Note:** As shown above, the constructor was updated to use `ChatModel` with `ChatClient.create(...)` (the **programmatic approach**) instead of `ChatClient.Builder`. This was needed because the project has both OpenAI and Ollama configured, which caused ambiguity — the same "multiple models" issue we solved earlier in the course using either `@Qualifier` or the programmatic approach.

## Step 5: Handling a Familiar Error — Multiple Embedding Models

Since this project has used **both OpenAI and Ollama** at various points in the course, restarting the application at this stage may bring back a familiar error: **ambiguity between multiple embedding/chat models**.

### The Fix

Just like before, this is resolved by either:

- Using `@Qualifier` to explicitly specify which bean to use, **or**
- Switching from the auto-configured `ChatClient.Builder` to the **programmatic approach**, explicitly injecting a specific `ChatModel` (as shown in the example above)

> This is a good reminder: whenever your project uses **more than one AI provider**, you're likely to run into this kind of bean-resolution conflict, and you'll need to explicitly tell Spring which implementation to use.

## Step 6: A Small Optimization — Avoiding Repeated Embedding on Every Restart

You may recall that our `DataInitializer` class (using `@PostConstruct`) automatically re-runs the entire embedding process **every time the application restarts** — reading the file, chunking it, generating embeddings, and storing them again.

While this is fine for testing, it does add unnecessary startup time and repeated API calls (and cost) if you're restarting frequently during development.

> **Practical tip:** During active development/testing (like when working on unrelated features, such as image generation), you can temporarily **comment out** the `@PostConstruct` annotation (or the initialization logic itself) in `DataInitializer`, to avoid re-running this process unnecessarily on every restart. Just remember to re-enable it when you actually need fresh data loaded.

## Step 7: Testing the Image Generation Endpoint

```
GET http://localhost:8080/image/Deadpool writing Java code
```

### What to Expect

- This request will take a little longer than usual (example: **10–12 seconds** or more) — since generating an image requires more processing time than a typical text response
- Once complete, you'll receive a **URL** in the response

### Viewing the Result

Since this URL points to an image hosted by OpenAI (specifically via **DALL·E**), you can simply **open this link in a browser** to view your generated image.

> **Fun observation from testing:** Asking for "Deadpool writing Java code" produced a fun, creative image — though, as often happens with AI-generated text within images, the "code" shown wasn't perfectly accurate Java syntax. This is a normal, common quirk of current image-generation AI — it's great at concepts and scenes, but often struggles with rendering readable, accurate text within the image itself.

## A Note on Image Quality and Customization

By default, the generated image may come back in a **standard** quality/resolution — not necessarily **high definition (HD)**.

You might also want to control other aspects of the generated image, such as:

- **Quality** (standard vs. HD)
- **Style** (example: natural-looking vs. more vivid/stylized)
- **Size/dimensions** (height and width)

These kinds of customizations are possible using something called **Image Options**, which we'll explore in the next topic.

## Quick Summary

| Concept | Meaning |
|---|---|
| `ImagePrompt` | Represents the input (text description) sent to an image generation model |
| `openAiImageModel.call(prompt)` | Sends the prompt to OpenAI's image model and returns an `ImageResponse` |
| `response.getResult().getOutput()` | Extracts the actual generated image result (typically containing a URL) from the response |
| DALL·E | The underlying OpenAI model that actually generates the image |
| Standard vs HD quality | By default, images may be generated in standard quality; higher quality/customization requires Image Options (next topic) |

## Practice Questions

**Q1: What class is used to represent the input (text description) for image generation, and what is the simplest way to create one?**
A: `ImagePrompt`. The simplest way is `new ImagePrompt(query)`, passing your text description directly as a `String`.

**Q2: What method is used to actually send the prompt to OpenAI's image model, and what does it return?**
A: `.call(prompt)` (called on `openAiImageModel`), which returns an `ImageResponse` object.

**Q3: How do you extract the generated image's URL from the `ImageResponse` object?**
A: By calling `response.getResult().getOutput()`, which contains the generated image's details, including its URL.

**Q4: Why did the "multiple embedding/chat models" error appear again in this topic, and how was it resolved?**
A: Because the project has both OpenAI and Ollama configured, causing ambiguity for Spring when trying to auto-inject a model. It was resolved by switching to the programmatic approach — explicitly injecting a specific `ChatModel` and using `ChatClient.create(...)`.

**Q5: Why might you temporarily disable the `@PostConstruct` data initialization logic during active development?**
A: To avoid unnecessarily re-running the entire embedding process (reading the file, chunking, generating embeddings) every time the application restarts, which adds startup time and repeated API calls/cost when you're not actually working on that specific feature.
